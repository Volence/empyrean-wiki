EMPYREAN / THE .EMP LANGUAGE / CONTRACTS

The .emp language

Contracts: what a procedure promises

Every routine in the engine makes promises to the code that calls it: these registers come back untouched, that one holds the answer, this one is scratch you can ignore. In hand-written assembly those promises live in a comment, and the machine never reads the comment. In .emp they live in the procedure header, where the assembler reads them, and the strongest of them stop the build the moment the code stops keeping them. This page teaches how to read one of those headers, clause by clause, says exactly which clauses are proved and which are inferred, and shows the checker refusing real mistakes from the shipping engine.

1 · The problem contracts solve

Start with the one fact the whole wiki keeps coming back to: the machine has no idea what anything is for. A subroutine does not know which register holds its input and which is scratch. The caller does not know which registers the routine will quietly stomp. None of that lives in the hardware. It lives entirely in an agreement between two pieces of code, and the only place that agreement is written down, in classic assembly, is a comment a human typed.

Here is a real one, from the Sonic 2 disassembly. It is the entry point for Nemesis art decompression, a routine the whole game leans on:

; Nemesis decompression to RAM
; input: a0 = art address, a4 = starting address of destination
NemDecToRAM:
        movem.l d0-a1/a3-a5,-(sp)
        lea     (NemDec_WriteAndAdvance).l,a3
s2disasm/s2.asm:1814

Read what that comment does and does not tell you. It names two inputs, and then it stops. It says nothing about registers, even though this routine is careful with them: that first instruction pushes thirteen registers onto the stack, and a matching instruction further down pops them back before the routine returns. So the routine really does make a promise, that those thirteen come back untouched, and the only place the promise is written down is the instructions themselves. A caller who wants to know has to read the body.

And nothing anywhere checks the comment. If someone later adds a line that trashes a2, which is one of the registers this routine does not save, the comment still says what it always said, the build still succeeds, and the bug ships. The comment cannot rot loudly. It can only rot silently.

Design decision · contracts are checked, or they are comments

What: .emp takes the sentence a good assembly programmer already writes in a header comment and moves it into the procedure header, where the assembler parses it and proves it against the body.

Why: a promise the tool cannot read is a promise nothing keeps. The engine had hundreds of these register agreements; a comment is the right place to explain intent and the wrong place to store a fact the build depends on. The taste behind the whole language is that a correctness feature is honest or it is absent, so if a claim can be checked, it becomes a contract, and if it genuinely cannot, it stays an ordinary comment and makes no promise it cannot back.

The cost, honestly: you write the contract, and sometimes the checker refuses code you believe is fine because it cannot yet prove the shape you used. That friction is the price, and the rest of this page is mostly about where it lands.

New here? · What is "the checker"?

When these pages say the checker, they mean the part of Sigil that reads procedure headers and compares each promise against what the instructions actually do. It is not a separate tool and it is not a runtime test: it reads the same source the assembler is turning into ROM bytes. But it works at two tiers, and they stop different things, so "the checker caught it" means one of two rather different sentences.

The per-file tier reads one module at a time and holds each procedure to its own header, using only that procedure's body. It runs on every build, today, always. Its error-tier findings, a preserves that is not restored, a flag result that overlaps a preserved status register, a with bracket a path escapes, stop the build with no ROM produced. Its warn-tier findings print and let the build finish. Every diagnostic quoted on this page is from this tier.

The whole-program tier is a walk over the entire corpus at once, following calls across module boundaries. It answers the questions no single file can: whether a register a caller was still holding survived a callee three levels down, whether a requires is satisfied at each call site, whether a declared cycle budget holds along the real path. That walk lives in Sigil's own test suite and in the strict gates a merge has to pass. It stops merges. Aeon's build.sh does not run it, so an engine build that closes an inferred hole is not what refuses; the merge is.

So the honest reading of "the build refuses" on this page is: the per-file tier refuses. Never "a test failed later" and never "someone noticed in review", but not the whole of the checking either.

Ratified, parcel in queue · the corpus walk moves into the build

The split above is a stage, not a destination. The direction is settled: the whole-program walk goes into the default build, not behind an opt-in flag, so that a contract hole that today survives to a merge gate will instead stop the build that created it.

The accepted semantics, so you know what to expect when it lands. The build will refuse any new closure violation. The residue that exists today, several dozen findings across the two inferred families, is pinned as a named legacy baseline and burned down over time rather than fixed in one sweep. And the families that already fire zero times on the corpus, [context.unsatisfied] and the survives family, gate as a hard assert-empty from the first day, because for those there is nothing to grandfather.

None of that is live yet. This page describes the compiler as it currently behaves.

New here? · What is a register contract even for?

A routine and its callers share a small number of registers. For them to cooperate they have to agree on who owns what: which register carries the argument in, which one carries the answer back, and which ones the routine is free to trample. That agreement is a register contract. It is not something the CPU enforces; the CPU will happily let a routine overwrite a register its caller was counting on, and the caller will happily read the garbage. Every classic assembly crash where "a value changed on its own" is one of these unwritten agreements getting broken. A .emp contract just writes the agreement down somewhere the build can hold both sides to it.

The .emp move is small to state and large in effect. Write the same sentence you would have put in the comment, but write it where the assembler can read it, and let the build fail when the code stops keeping it. The rest of this page is the vocabulary for that sentence: which registers die (clobbers), which survive (preserves), which carry answers (out), what the routine needs to be true before it runs (requires), and the two kinds of check that guard the build itself (ensure and assert).

Teaching example · not engine code

The failure mode in miniature: a routine's comment says ; d3 preserved, someone later adds move.w #0, d3 in the middle of it, and in assembly both lines sit there without complaint while the next caller that trusted d3 reads a zero it never expected. The whole point of a contract is to make that exact edit refuse to build, and by the end of section 3 you will watch it do so.

2 · clobbers: the honest list

Start with the simplest clause, because it is one dumb mechanism. clobbers(...) lists the registers a routine destroys. Everything not on the list, and not an argument, and not a declared result, is promised to come back exactly as it went in. That last part is the half people miss: the list of what dies is also, by omission, the list of what lives. An empty clobbers() is a strong promise, not a lazy one. It says this routine destroys no caller register at all.

Two real headers from the engine. The first posts a byte to the sound driver and swears it leaves every data and address register alone:

pub proc Sound_PostByte (d0: u16, a0: *u8) clobbers() preserves(sr) {
aeon/engine/sound/sound_api.emp:104

The second decompresses a block and is honest that it burns two data registers as scratch while protecting the rest:

pub proc ZX0_Decompress (a0: *u8, a1: *u8) clobbers(d0-d1) out(a0, a1) preserves(d2/a2) {
aeon/engine/compression/zx0.emp:58

Read the second one as a caller. It tells you, without opening the body, that d0 and d1 come back as garbage, that a0 and a1 hold results you are meant to use, and that d2 and a2 are untouched. That is the entire value of the clause: you schedule your own register use around it having read one line.

New here? · Why is leaving a register OUT of the list also a promise?

Because the checker treats every register a proc writes as needing a reason. There are only four legal reasons: it is listed in clobbers (destroyed on purpose), it is a declared out result, it is an argument the routine is allowed to consume, or it is saved and restored so it ends the call unchanged. A register that is none of those and still gets written has no home, and the checker says so. So an omitted register is not "unspecified," the way an omitted comment would be. It is a positive claim: this one survives. The clause you did not write is doing as much work as the clause you did.

So what happens when the body breaks that? Say a routine declares clobbers(d1) and then writes d3, which is neither a clobber nor an argument. The checker prints this and the build carries a warning:

Warning[proc.clobber-undeclared] `Sfx_Post` writes `d3`, which is not in its `clobbers(...)` set or parameter list (heuristic lint - full register dataflow is deferred to S2-D6)

It is a warning, not a hard error. The proof it rests on is a heuristic: the assembler recognises the write forms it can, and full register dataflow is deliberately deferred, so an undeclared clobber is flagged loudly rather than made unbuildable. It still names the exact register and the exact routine. (Sfx_Post is the procedure in the interactive checker below.)

Which raises the fair question of what the real engine's warn tier looks like, and the answer is pinned in Sigil's test suite so it cannot drift quietly. Exactly four warn-tier classes fire on the shipping corpus: [proc.clobber-undeclared], [proc.out-unwritten], [proc.undeclared-fallthrough], and [module.path-mismatch]. The set is frozen per build shape, so retiring a class or admitting a new one is a deliberate one-line edit rather than something that happens by accident. The shipping ROM builds green with those warnings present, by design. They are known-open lint classes, each triaged, and listing one says "known", not "fine".

Design decision · the honest default is "survives"

What: a register you never mention is presumed preserved; writing it without declaring it is what draws the warning.

Why: the language's stance is explicit-by-default and release-ready: the reading that protects a caller should be the one you get for free, and the destructive reading should be the one you have to spell out. A default of "anything might be trashed" would make every clause meaningless, because a caller could rely on nothing.

The cost, honestly: because full dataflow is future work, the undeclared-write check is a warning today, so a lying clobbers can technically still assemble. A default build makes that quieter still: it prints a tally of the warn tier by lint class rather than the individual messages, and you set SIGIL_WARNINGS=full to read them. The stricter, provable clause is preserves, which is next, and it is a hard error.

3 · preserves: a promise with a proof

Every register a proc touches has to have a reason, and there are four of them: preserves (comes back untouched), clobbers (destroyed scratch), out (a result the caller reads), and the fourth, which section 2's explainer named in passing and which deserves saying outright: an input, declared by the typed parameter list and by nothing else.

The parameter case has a rule of its own, and missing it is the commonest way to misread a header. A parameter register may be freely read: the parameter list alone licenses that, and no other clause is needed. But if the routine writes a parameter register, the write has to be declared like any other. Which clause depends on what the new value means. If it is a result the caller should read, say out. If it is garbage left behind, say clobbers. If it genuinely round-trips, say preserves and let the checker prove it. So a register appearing in both the parameter list and clobbers is not a contradiction, it is the normal spelling for "comes in carrying an argument, goes out carrying nothing", and around forty procedures in the engine are written exactly that way, QueueDMA_Deferrable (d1: u32, d2: u16, d3: u16) clobbers(d0-d4/a1-a2) among them.

The in-out pointer pattern is the same rule with a different answer. ZX0_Decompress (a0: *u8, a1: *u8) ... out(a0, a1) takes its source and destination pointers in and hands them back advanced past the data it consumed and produced, so the write is a result and the clause is out. DrawRings (d5: u16, a4: *u8) ... out(d5, a4) does the same with its buffer cursor. Reading such a header, out on a parameter register is the signal that the value you passed in came back changed on purpose.

Of the four, preserves(...) is the interesting one, because unlike a bare clobber list it is a claim the checker proves rather than trusts. It holds only if, on every path out of the routine, each listed register carries the same value it had on entry.

Almost always the proof is the save-and-restore bracket you already write by hand: push the register at the top, pop it at the bottom. The checker recognises the pair and, if the value that comes back is the one that went in, the promise stands.

New here? · What is a save/restore bracket?

If a routine needs a register that its caller is using, the polite move is to borrow it: copy the old value somewhere safe on entry, use the register, and copy the old value back before returning. On the 68000 that "somewhere safe" is the stack, and the two halves are usually a movem push at the top and a matching movem pop at the bottom. The two together are a bracket around the borrowing. preserves is the checker verifying that the bracket is actually closed on every way out, so the register a caller lent really does come home. If you have not met the stack yet, the 68000 track's stack section teaches it in full.

Here is the bracket doing exactly that inside ZX0_Decompress, the proc whose header section 2 quoted, protecting two registers across a decompression loop:

        movem.l a2/d2, -(sp)            // preserve registers
        // ... the decompression loop ...
    .done:
        movem.l (sp)+, a2/d2            // restore preserved registers, fall into the shared rts
aeon/engine/compression/zx0.emp:59,120

Now the part that makes preserves a hard error rather than a warning. If a register is on the preserve list, gets written in the body, and is not brought back to its entry value, the checker refuses to build the ROM:

Error[proc.preserves-unverifiable] `Sfx_Post` declares `preserves(d2)` but `d2` is written and not restored

The diagnostic code names the stance: unverifiable. The checker is not claiming your routine is definitely wrong; it is refusing to certify a promise it cannot prove. The language's rule, stated in the checker's own source, is that a wrong contract is worse than no contract, so an unprovable preserve fails hard. It is better to have written nothing than to have written a promise the caller will trust and the code will break.

The status register is two promises, not one

One register on the 68000 deserves its own treatment: the status register. It packs two unrelated things into one word. Its low half holds the condition codes (the X N Z V C flags an ordinary instruction sets), and its high half holds the interrupt mask among the supervisor bits. A routine very often wants to promise one half and not the other, so .emp lets you name them separately: preserves(sr.ccr) is a promise about the flags alone, preserves(sr.mask) about the high byte alone, and preserves(sr) covers both.

Read sr.mask as naming the whole system byte, not just the three interrupt bits its name is borrowed from. That byte holds the interrupt mask, and it also holds the trace bit and the supervisor bit, and the promise covers all of them, because they share a byte and no instruction can write one without going through the others. The name is short for the bit-field everyone actually cares about; the guarantee is byte-wide. Sigil's own definition says exactly this, and so does the tooltip on "status register" above.

This routine keeps the system byte exactly where it found it while treating the condition-code flags as scratch it is allowed to change, and the precision earns its keep in section 7's third war story, where a routine claimed to preserve the whole status register while quietly returning an answer in the carry flag, which lives inside the half it swore not to touch:

pub proc Sound_DrainSfxRing () clobbers(d0-d1/a0/sr.ccr) preserves(sr.mask) {
aeon/engine/sound/sound_api.emp:349
Design decision · the status register splits into mask and ccr

What: preserves and clobbers accept sr.mask and sr.ccr as separate tokens, and the two halves are checked independently, so preserves(sr.mask) clobbers(sr.ccr) is a legal, non-contradictory header.

Why: preserving the flags and preserving the interrupt mask are different jobs with different proofs, and folding them into one sr token forced routines to over-claim. A routine that legitimately changes flags but carefully protects the interrupt level could not say so, and the honest thing it did every day had no honest spelling.

The cost, honestly: a bare preserves(sr) now has to earn both halves. When the checker cannot prove the flags come back intact, it downgrades that claim to a warning and suggests sr.mask, which is the checker nudging you toward the smaller promise you can actually keep.

4 · Arguments and results with names

A contract has two more sides: what goes in, and what comes back. Both get names.

The inputs are the typed parameter list right after the proc name. When a header reads (d0: u16, a0: *u8), that is the input contract in full: d0 carries an unsigned word, a0 carries a pointer to bytes. There is no separate keyword for inputs; the typed parameters are the input clause. If you go looking for an in(...) clause because some other systems have one, there isn't one here, and that is deliberate.

The outputs are the out(...) clause. It lists registers the routine produces for the caller to read, and it can also name a flag as a result. That last form is the one worth dwelling on, because a flag carrying an answer is where the "these are just comments" idea dies hardest.

New here? · How can a flag be a result?

A routine does not have to return its answer in a register. Sometimes the answer is a single yes-or-no, and the cheapest place to put a yes-or-no is a condition code: the routine sets or clears the carry flag on its way out, and the caller immediately does a bcs or bcc to react. It is the same trick a cmp followed by a branch uses, except the "compare" is a whole routine's worth of work. .emp lets the header say so: out(carry: full) means the carry flag comes back carrying a real answer, and full is just a caller-facing name for what a set carry means here. The flags themselves are taught on the Math & Logic page.

Here is the page's clearest example, and it is best read as a pair. First the producer: a routine that appends a ring to a shared buffer and reports back, in the carry flag, whether the buffer was full.

pub proc RingBuffer_Add (d0: u16, d1: u16, d2: u8, d3: u8) clobbers(d4, a0) out(carry: full) {
        moveq   #0, d4
        move.b  Ring_Count, d4
        cmpi.b  #MAX_RING_BUFFER, d4
        bhs     .full
        // ... append the entry, then:
        andi.b  #$FE, ccr               // clear carry
        rts
    .full:
        addq.b  #1, Ring_Add_Dropped
        ori.b   #1, ccr                 // set carry
        rts
}
aeon/engine/objects/rings.emp:58

The header promises a flag answer, and the two rts paths deliver it: the success path clears carry, the full path sets it. Now the consumer, in the routine that offers one ring to the buffer and has to know whether it landed:

        jbsr    RingBuffer_Add          // clobbers d4, a0
        bcs     .gated                  // full - no bit; re-scan/populate retries
        moveq   #0, d0
        move.b  EntityScanState.ess_entry_idx(a1), d0
        // ... success path: set the loaded bit
        jbsr    EntityLoaded_Set
    .gated:
aeon/engine/objects/entity_window.emp:1035

The bcs .gated on the line right after the call is the whole reason the flag result exists. The caller branches on the carry the callee promised. Producer and consumer sit in two different files, and the contract is the only thing tying them together: the header says an answer rides home in carry, and the caller reads exactly that. Move the answer to a different flag without updating the header and the two halves disagree, which is precisely the kind of drift the checker exists to catch.

Named misconception · "the types are for the assembler's benefit"

It is tempting to read (d0: u16, a0: *u8) as bookkeeping the assembler wants. It is the opposite. The assembler does not need the word "u16" to emit a move; the instruction already encodes its size. The parameter types and the out clause are written for two readers: a human, who now learns the calling convention from one line instead of from the body, and the checker, which holds callers to it. The names are the point. A register with a role stated is a register the build can defend.

One detail worth knowing, because it is the shape most out pointers actually use. The checker counts (a4)+ and -(a4) as writing a4, in any operand position and under any mnemonic. So move.w (a4)+, d0 writes both d0 and a4, and tst.w (a0)+ writes a0 even though tst reads. That is what lets a pointer advanced only by auto-increment carry an honest out(a4), and it equally means a routine that scribbles a pointer this way cannot slip past the undeclared-write lint. The one exception is a7 moved by (sp)+ or -(sp), which is stack discipline rather than a register effect, and is exempted deliberately.

5 · requires: promises about the world

The clauses so far are promises about registers. Some routines also need a promise about the state of the machine: a thing that must already be true when they run, that no register can express. .emp calls those contexts, and there are two flavours, with quite different amounts of proof behind them. Learn the strongly-checked one first.

New here? · What is a context, and who grants it?

A context is a named fact about the machine that a routine can require and another can provide. An acquired context is one the code creates itself with a bracket: it writes the setup instructions, does its work, and writes the teardown, and the compiler both supplies those instructions and proves the bracket is closed. A granted context is one only the hardware can bring about; the code cannot fake it, so the routine the hardware genuinely enters at the right moment is trusted to declare it, and everything downstream either has it or gets refused. Either way the value of a context is the same: it lets a routine state a precondition the type of a register could never carry.

Acquired contexts: the bracket the checker watches

Start with a real hardware requirement, because it is the clearest case of a rule no register can express. On a Genesis, reading the controller ports is not safe while the Z80 is running: Z80 traffic on the 68000 bus corrupts reads from the $A100xx I/O range. Sega's own Technical Bulletin gives the sequence, and it is not optional. Request the Z80 bus by writing $0100 to the bus-request register, spin until the Z80 actually hands it over, do your I/O, then write $0000 to give it back.

In .emp that whole sequence is a context named z80_stopped, and the routine that needs it simply says so:

pub proc Read_Controllers () clobbers(d0-d4/a0) requires(vblank) {
        with z80_stopped {                  // unconditional - see header trace
            lea     HW_PORT_1_DATA, a0
            // ... the whole two-port six-button burst ...
        }
        rts
}
aeon/engine/system/controllers.emp:29-59 (abridged) 
pub context z80_stopped {
    // Request the bus and spin until the Z80 grants it.
    acquire = asm {
        move.w  #$0100, Z80_BUS_REQUEST
    .wait_z80:
        btst    #0, Z80_BUS_REQUEST
        bne     .wait_z80
    }
    // Release it.
    release = asm {
        move.w  #$0000, Z80_BUS_REQUEST
    }
}
aeon/engine/z80_bus.emp:24-36

Three things about that are worth stating separately. The bracket is unconditional: it is not gated on whether the sound driver happens to be built in, because both build shapes reach that code with the Z80 running. The reason is written in the source as a comment naming the hardware bug, so a later reader cannot mistake it for caution. And the properties of the bracket, unlike much on this page, are genuine error-tier checks: every path through the body must reach the release, no branch may jump into the middle of the region, and the hold may not be taken twice.

Contexts are declared once and used everywhere. Here is the other one the engine leans on, ints_off, whose two halves are the instructions that raise the interrupt mask and the instruction that restores it:

pub context ints_off {
    acquire = asm {
        move.w  sr, -(sp)
        move.w  #$2700, sr
    }
    release = asm {
        move.w  (sp)+, sr
    }
}
aeon/engine/irq.emp:48

You never write those halves at a call site. You write a with block, and the assembler splices the acquire in at the top and the release in at the bottom. Here is a real one, masking interrupts and holding the other CPU's bus around a single byte write:

pub proc Sound_PostByte (d0: u16, a0: *u8) clobbers() preserves(sr) {
        with ints_off {
            with z80_stopped {
                move.b  d0, (a0)
            }
        }
        rts
}
aeon/engine/sound/sound_api.emp:104

Here is what makes the block worth more than writing the two halves by hand: the checker proves that every path through the body reaches the release. If any path leaves the bracket without running the release, the interrupts stay masked forever after, and the checker refuses it:

Error[context.escape] this path leaves the `with ints_off` region without reaching its release - the context stays held past the bracket

An early rts inside the block, a branch to a label outside it, a tail call out of the middle: all of them are escapes, and all of them fire this error. This is the exact mistake the third edit in the contract checker above stages, so if you have not toggled it yet, that message is what it produces.

Honesty about scope: some brackets in the engine are still written by hand on purpose, where the shape genuinely defeats the automatic proof. The checker does not pretend to handle those; it handles the common bracket exactly and leaves the rare one to the programmer, clearly marked.

Granted contexts: requires, and a scheduling rule

Now the other flavour, and go back to that same Read_Controllers header, because it carries one of each and they are not the same kind of claim:

pub proc Read_Controllers () clobbers(d0-d4/a0) requires(vblank) {
aeon/engine/system/controllers.emp:29
Two claims, both true, of different kinds

The with z80_stopped bracket is a hardware requirement: the pads cannot be read correctly with the Z80 on the bus, on any Genesis, in any program. The requires(vblank) is a scheduling rule: Aeon has decided that the pads are sampled once per frame, during VBlank, so that every system that reads them sees the same snapshot. Nothing in the silicon says pads must be read in VBlank. Both claims belong in the header, and reading a header well means knowing which sort you are looking at.

The word vblank names a context declared elsewhere. The interrupt handler that runs at the top of VBlank, VBlank_Handler, is marked as granting it, and the checker then enforces the consuming side across the corpus: a call to Read_Controllers from a place that does not have the granted vblank window is reported at the call site as [context.unsatisfied]. That check lives in the whole-program walk described at the top of this page, so it is one of the findings that today stops a merge rather than a build. On the current engine it fires zero times.

Watch out · a granted context is a trust root, not a proof

The checker enforces that a requires(vblank) routine is only called from inside a vblank window, but it cannot verify that the routine which grants vblank really does run during the blanking interval. That is a hardware fact no assembler can check, so grants is an explicit trust root: one place where the code says "take this as given." The language does not hide that it is trusted rather than proven. Everything downstream of the grant is checked; the grant itself is the human's word.

Watch out · the vblank chain has an unchecked link today

Be concrete about what "everything downstream is checked" currently covers, because in this very chain it does not reach all the way. VBlank_Handler grants vblank, but it does not call the frame's work directly. It loads a routine pointer and dispatches through it, jsr (a0) as VBlankHandler, and the contract type it names carries no requires. The walk follows calls by name, and a computed dispatch has no name to follow, so that edge is not walked: the requirement is not propagated across it, in either direction.

The engine does have a way to tell a computed jump what it may land on, a targets(...) clause listing the physical destinations, and one jump in the engine carries one. The whole-program walk does not consume it yet. A parcel to close this, so that a dispatch with declared targets propagates contracts along each of them, is queued. Until it lands, treat a requirement that has to cross an indirect dispatch as documented rather than proved.

6 · ensure and assert: two clocks

Everything so far is checked at build time. But .emp has a second kind of check, and telling the two apart is the whole lesson of this section: some things the tool can decide while it is building the ROM, and some things are only knowable while the ROM is running. .emp gives each its own keyword, and the difference between them is when the check happens.

New here? · Build time and run time are two different clocks

Two moments in a piece of code's life are easy to blur together. Build time is when the assembler turns your source into a ROM: it happens once, on your machine, before any hardware sees the code. Run time is every moment afterward, when the Genesis is actually executing the ROM. A fact like "these two constants agree" is settled at build time and can never change once the bytes are fixed, so it is wasteful and pointless to check it on the console. A fact like "this buffer never overflowed during play" is not knowable until the game runs. Good tools check each fact on the clock where it lives, and .emp has one keyword for each.

ensure(...) is the build-time check. It states a condition the assembler must be able to evaluate while building; if the condition is false, the build stops and no ROM is produced. It is most often used to lock two authorities together so they cannot drift apart. This one refuses to build if the engine's idea of the VRAM target code disagrees with the constant the rest of the toolchain exports under the same name:

ensure(target_bits(VdpTarget.Vram) == extern("VRAM"),
       "engine.constants and engine.vdp disagree on VRAM - update target_bits")
aeon/engine/vdp.emp:69

assert is the run-time check, and it is only present in the debug build. It desugars into real instructions that test a condition on the actual hardware and, if the condition fails, drop into the debugger. In the plain release ROM those instructions are simply not emitted, so the check costs zero bytes in the shipping game. This one lives in the ring buffer's overflow path and fires, in debug, if a ring was ever dropped, because a drop means a content bug upstream:

    .full:
        addq.b  #1, Ring_Add_Dropped
        if DEBUG == 1 {
        move.b  Ring_Add_Dropped, d4    // d4 = declared clobber
        assert.b d4, eq, #0             // drop = content bug, fatal in DEBUG
        }
        ori.b   #1, ccr                 // set carry
        rts
aeon/engine/objects/rings.emp:86
Design decision · a build-time check never survives to run time

Why: a correctness check should be free where it can be. If the assembler already knows the answer, spending a runtime instruction to re-ask on the console is pure waste, and worse, it invites the habit of shipping debug scaffolding in the release ROM. Splitting the keywords by clock makes the free check free and the costly check opt-in.

The cost, honestly: you have to know which clock your fact lives on. A condition that depends on runtime state cannot be an ensure, and a constant relationship put in an assert wastes debug cycles checking something that could never vary. The keyword you reach for is a small design decision each time.

7 · When the checker catches you

The argument for checked contracts is not that they are tidy. It is that they catch real lies in real shipping code, contracts that a careful programmer wrote and believed. Here are three the checker found in the engine. Each is the same arc: what the header claimed, what the code actually did, how the checker said no, and the fix.

New here? · What is a "false contract"?

A false contract is a header that promises something the body does not deliver: a register listed as preserved that actually gets trampled, a flag sworn untouched that is really changed, a routine claimed to never return that has a way out. It is not a typo and not a crash; the code often runs fine in the case the author tested. It is a promise that is true today and becomes a trap the moment a caller relies on it in a case the author did not try. These three all looked correct to a careful reader and shipped anyway, which is exactly why a tool that reads the promise is worth having.

The PSG divisor that lied about a register

The claim. A small Z80 routine in the sound driver, Psg_EmitDivisor, declared preserves(b): register b comes back untouched.

What the code did. The routine does not end with a return. It falls straight into the next routine, Psg_EmitDivisorTo, whose first job includes ld b, a, which overwrites b. Because control runs off the end into that successor, the value of b a caller would see is the trampled one, not the preserved one. The promise was false, and it had shipped in the driver.

How the checker said no. The clause that catches a preserved register that is not brought back is the hard [proc.preserves-unverifiable] error from section 3. The subtlety here is that the damage happens in a routine the falling-through proc runs into, so the check has to charge a proc's exit against the routine it falls into rather than stopping at the last instruction. Once it did, the lie surfaced with a live witness.

The fix. The header was corrected to tell the truth about what the fall-through costs. It now reads:

pub proc Psg_EmitDivisor () clobbers(a, b, c, f) preserves(de, hl) falls_into Psg_EmitDivisorTo {
aeon/engine/sound/sound_psg.emp:430

The moral. A contract is only as good as the control-flow model behind it. The routine that runs off the end is as much a part of your exit as your own last instruction, and the checker has to know it. When the model learned that, the false promise could not survive.

Four routines that swore off a flag they were changing

The claim. Four routines, among them VSync_Wait and Sound_PlayMusic, each declared bare preserves(sr): the whole status register comes back untouched, both the interrupt mask and the condition-code flags.

What the code did. Each of them wrote a condition-code flag on a path to rts that lay outside its save-and-restore bracket. The interrupt-mask half of the promise was fine; the flags half was false, because the flags were genuinely different on the way out.

How the checker said no. Because the status register splits into two halves that are checked independently, the checker could see that the mask half held while the flag half did not. A bare preserves(sr) whose condition-code half is not provably the caller's draws the advisory that names exactly this and suggests the smaller, true promise:

Warning[proc.ccr-advisory] `VSync_Wait` declares bare `preserves(sr)` (both halves), but its condition codes are not provably the caller's at return: ... - declare `preserves(sr.mask)` if only the interrupt mask round-trips (path-sensitive flag liveness is S2-D7)

The fix. All four were flipped to the honest preserves(sr.mask): keep promising the interrupt mask, stop promising the flags. Two of them had actually been given the bare sr form by an earlier convention, so the fix overturned a rule that had once been accepted.

The moral. Precision in the contract vocabulary is not decoration. Because .emp could say "the mask, not the flags," the routines could tell a true small promise instead of a false large one, and the checker could tell the difference.

The routine that preserved the flag it was returning

The claim. QueueDMA_Deferrable returned a yes-or-no in the carry flag, declared out(carry: dropped), and also declared preserves(sr): the whole status register comes back untouched.

What the code did. The carry flag lives inside the condition-code half of the status register. So the header promised to return an answer in carry and, in the same breath, promised to leave carry exactly as the caller had it. Those cannot both be true. A returned flag is changed by definition; a preserved one is not.

How the checker said no. The overlap between a flag result and a preserved status register is a hard error, caught the first time the routine was checked:

Error[proc.out-preserves-overlap] `QueueDMA_Deferrable` declares `out(carry: dropped)` and preserves the condition codes (bare `sr` covers both halves) - a flag result lives in CCR, so CCR either carries the result or is restored to entry, not both (declare `preserves(sr.mask)` if only the interrupt mask round-trips)

The fix. The header became out(carry: dropped) preserves(sr.mask): return the answer in the flags, promise only the interrupt mask. You can read the corrected line in the engine today at aeon/engine/system/dma_queue.emp:106.

The moral. This is the payoff of the two-halves split from section 3, shown as a bug rather than a feature. A single-token sr could not even express the contradiction, so the tool could not see it. Splitting the register let the routine state what it meant, and the instant it did, the tool could tell that what it meant was impossible.

8 · Escape hatches, and what refuses them

A checker this strict needs pressure valves, or it stops being adopted. .emp has two, and the interesting fact about them is not that they exist but which findings they can reach.

@allow("group", "reason") silences one named lint group, at a module or a proc, and for the group that opts out of analysing a computed-dispatch site the parser insists on a written reason. @as_compat is the faithful-port valve: on a module still being carried over verbatim from the old assembler, it softens the inferred lints, so a literal transcription can build before it is cleaned up.

Design decision · declared claims cannot be silenced; inferred ones can

What: the line runs between a claim you wrote and a finding the compiler derived. Violating a declared contract, a preserves, an out, a requires, a budget, has no suppression flag at all. So do the structural contracts around them: a falls_into that does not line up, an escaped with bracket, a proc marked never-returning that returns. No attribute turns any of those off. Inferred-only findings, on the other hand, the stack analyses, the live-clobbered check, the blind-call warnings, do get @as_compat softening and per-site @allow, and that is by design rather than by omission.

Why: the two cases are not symmetric. A declared contract is the author's own claim about their own code, so violating it is never a false alarm; it is either the header being wrong or the body being wrong, and both want fixing. An inferred finding is the compiler's guess about code it does not fully model, and on this hardware a deliberate low-level technique can look exactly like a mistake, so refusing it outright would make the tool wrong about correct code with no way out. Hence: proofs are absolute, guesses are appealable.

The cost, honestly: occasionally the checker refuses code that is actually correct in a way it cannot yet prove, and for a declared contract there is no override. The answer is to write the code in a shape the checker can follow, or to widen the contract to the honest weaker claim, never to silence the proof. That is friction on purpose.

What it costs in practice: nothing so far. Across the whole engine and both games, at the revision this page describes, there are zero uses of either hatch. The only @allow in the corpus silences a data-layout lint, not a contract finding, and there is no @as_compat anywhere.

That is the vocabulary this page has taught, and a .emp procedure header is a sentence in it: clobbers for what dies, preserves for what survives with a proof behind it, typed parameters and out for what goes in and comes back, requires for what must be true of the machine first, and ensure and assert for the two clocks. A header can carry more than these. falls_into names the routine control runs off the end into, and section 7's first war story is about why the checker has to know it. grants is the trust root that hands out a context. @noreturn marks a routine with no way back, and around twenty procedures across the two CPUs carry it. @budget(cycles: n) declares a machine-checked cycle ceiling: exactly one procedure in the engine has earned one so far, the critical DMA drain, at 670 cycles. None of it is a comment. Every clause is a claim, and for the declared ones the build will hold you to it.

So go read one. Every .emp excerpt on the engine pages is now legible as a set of promises: open the Reading .emp page again, or any header quoted here, and this time read the top line as a contract. Someone wrote it, a tool read it against the code, and for the proved clauses it is still true because it could not have shipped otherwise. That is the entire argument for writing it down where the tool can see it.
