The .emp language

Reading .emp

The Aeon engine is not written in raw assembly and it is not written in C. It is written in .emp, a language whose procedure bodies are the exact 68000 and Z80 instructions you already know, wrapped in a structure the assembler can check. This page teaches you to read one: after it, every .emp excerpt on this wiki parses in your head, and you can tell at a glance which lines are for the assembler, which are checked promises, and which are instructions the CPU runs.

1 · What .emp is

.emp is the source language the Aeon engine is written in, for both of the Genesis's processors: the 68000 that runs the game and the Z80 that runs the sound. Nearly every module of the engine, and of the games built on it, is .emp; the exceptions are countable, and at the revision this page describes they are three files, the vendored MD Debugger island and one root file per game. Source becomes ROM bytes by way of Sigil, the project's own assembler. There is no separate C layer and no runtime underneath: what you read is what runs.

Sigil began by earning trust the hard way: before it added a single new idea, it reproduced the engine's ROM byte for byte, identical to the output of the old assembler it replaced. Only once it could do that did the language grow on top. That order means every feature .emp adds is something you could have written by hand in plain assembly, made safer or shorter, never something magic bolted on that you cannot see through.

So the taste of the language is: the same instructions you already know, plus a structure the assembler can check. And this is the one idea to carry through the whole page, because it is the thing newcomers get wrong first. The extra lines around the instructions, the ones naming which registers a routine may change and which it must hand back untouched, are not comments. They are checked, and the strongest of them have real teeth: break a promise to preserve a register and the build fails outright, with no ROM. The sections ahead show the checker doing exactly that.

One thing to fix in your head now, because both this page and the next depend on it. The checking happens at two tiers, and they stop different things. The first tier reads one file at a time and compares each procedure header against that procedure's own body; it runs on every build, and its error-tier findings stop the build with no ROM. The second tier is a whole-program walk that follows calls across module boundaries and answers questions no single file can, such as whether a register a caller was still holding survived a callee three levels down. That walk runs in Sigil's own test suite and in the strict gates that guard a merge, so today it stops merges rather than builds. Whenever a page here says the build refuses something, it is the first tier being described. The direction is settled: the whole-program walk is ratified to move into the default build, with a parcel queued to do it. It has not landed, so this page describes it as it currently runs.

New here? · What is an assembler, anyway?

A CPU only understands numbers: each instruction is a pattern of bits. Writing those by hand is unbearable, so from the very beginning programmers wrote instructions as short words (move, add, jmp) and let a program translate the words into the numbers. That translator is an assembler, and the words are assembly language. One line of assembly is usually one instruction for the CPU.

Sigil is an assembler, so most of what it does is that same faithful translation, one line to one instruction. What is new is that it also reads the extra structure .emp lets you write and checks that the code keeps the promises it makes. When a per-file check finds a procedure whose header and body disagree at error tier, it refuses to produce a ROM at all. If you have never met assembly at all, the 68000 programming model and the Z80 programming model pages start from zero.

New here? · Wait, are these annotations just comments?

This is the single most common first misreading, so it is worth stating plainly. When you see a line like clobbers(d4, a0) attached to a routine, it looks like documentation: a note to a human saying "this routine messes up d4 and a0". In most assembly, that is exactly all such a note could ever be, because the assembler has no idea what the routine really does; a comment can lie forever and nothing notices.

In .emp that same line is a contract, and the assembler reads it. It works through the routine's instructions, derives which registers actually get changed, and compares that to what the line claims. Two different things happen next, and it is worth knowing which is which from the start.

Break the firm promise to hand a register back untouched, the preserves clause, and the build stops outright with no ROM. That claim is proved: the checker traces every path out of the routine and either sees the value round-trip or refuses to certify it.

Write clobbers(d4, a0) and then also scribble on d3, and you get a warning instead. Undeclared writes are found by pattern recognition over the instruction forms rather than by a full dataflow proof, so the checker names the register and the routine but lets the build finish. A default build even prints only a tally of how many warnings fired and in which classes; you need SIGIL_WARNINGS=full to read the individual messages. So a clobbers list can still technically be wrong and still assemble.

That is the honest shape of it, and it is why this page reserves words like "proved" for the clauses that really are proved. What every contract does guarantee, even the warned kind, is that it is read: a comment can rot in silence forever, and one of these cannot.

Decision Adoption over cleverness: keep the assembly body, modernize only the shell. A language could have replaced move.w and bne with something higher level. .emp deliberately does not. Inside a routine, the instructions are ordinary 68000 or Z80, cycle for cycle, so a programmer who knows the CPU reads a routine body unaided on the first day and can predict its exact bytes and timing. Only the shell around the instructions, the module boundaries, the routine headers, the build-time values, is new. The honest cost: you must learn that new shell, which is what this page and the next few teach; the payoff is that you never have to wonder what the machine is really doing, because the machine part never changed.
Decision A promise the tool can check becomes a contract; one it cannot stays a comment. The rule the language holds itself to sorts every claim by whether a tool can back it. If the assembler can verify a claim, that claim is written as a checked contract, not prose, so it can never drift out of date. If a claim cannot be checked (an assumption about the hardware, a note about intent), it stays an ordinary comment and makes no promise it cannot keep. The cost is bluntness. Sometimes you must either prove a thing or admit you are only asserting it; there is no comfortable middle where a hopeful claim looks official.

2 · A real file, top to bottom

The fastest way to learn to read .emp is to read a real file, so here is one: the engine's ring buffer, which tracks the rings scattered through a level. We will walk it from the top, one kind of line at a time. Every excerpt below is the engine's actual source, quoted verbatim except where the caption under it says otherwise; the two that are trimmed say so, one abridged and one with its comments dropped. Nothing is paraphrased or invented, and anything that is not engine source at all carries the dashed "teaching example" border instead of a source line.

A .emp file is a module, and it opens by saying so. The first two lines name the module and pull in the names it borrows from elsewhere:

module engine.objects.rings in rings

use engine.objects.sst.{Sst}
engine/objects/rings.emp:9,11

The module line gives the file a dotted name (engine.objects.rings) and says its code belongs to a ROM region called rings (more on that in section 5). The use line imports one specific name, Sst, from another module. There is no list of files to include in a fixed order and no header-guard ritual; you name what you want and the assembler resolves it. Everything a module declares is private to that module unless it is marked pub (public), the way Sst's home module must have marked it to let this file borrow it.

New here? · What is a module, and what does importing mean here?

A module is just one .emp file, treated as a self-contained unit. The names it defines (routines, constants, data) live inside it and do not leak out unless it says pub. That is the opposite of classic assembly, where every label is visible to every other file whether you meant it or not, and two files accidentally using the same label name is a real and nasty bug.

Because names are private by default, a file that wants to call a routine from another module must ask for it by name with use. There is no separate linker script you have to keep in sync: the use line is the request, and the assembler connects it to the one public definition that matches. If the name is not public, or does not exist, that is an error you hear about at build time, not a mystery crash later.

Next come the module's values. A const is a build-time value: a name for a number that the assembler substitutes wherever it is used. Nothing in the ROM is labelled RING_WIDTH; the number 16 is simply baked into every instruction that refers to it.

const RING_WIDTH             = 16
engine/objects/rings.emp:33

Then the routines. Here is the one that appends a ring to the buffer. Read the first line carefully, because it is the header that makes .emp different from plain assembly, and then read the body, because the body is plain assembly:

pub proc RingBuffer_Add (d0: u16, d1: u16, d2: u8, d3: u8) clobbers(d4, a0) out(carry: full) {
        moveq   #0, d4
        move.b  Ring_Count, d4
        cmpi.b  #MAX_RING_BUFFER, d4
        bhs     .full
        // a0 = &Ring_Buffer[count * 6]
        move.w  d4, -(sp)
        // ... store the ring's fields, then return with carry clear ...
    .full:
        addq.b  #1, Ring_Add_Dropped
        if DEBUG == 1 {
        move.b  Ring_Add_Dropped, d4    // d4 = declared clobber
        assert.b d4, eq, #0             // drop = content bug, fatal in DEBUG
        }
        ori.b   #1, ccr                 // set carry
        rts
}
engine/objects/rings.emp:58-98 (abridged; full walk below)

The header reads left to right as a set of promises. pub proc RingBuffer_Add declares a public routine. (d0: u16, d1: u16, d2: u8, d3: u8) is its input contract: it expects a 16-bit value in d0 and d1, and a byte in d2 and d3. clobbers(d4, a0) promises those are the only registers it destroys as scratch. out(carry: full) says it returns a result in the carry flag, and gives that result a caller-facing name, full. Every one of those clauses is checked against the body. The details of what each clause means, and how far the checker can prove each one, are the next page's whole subject; here you only need to recognize the shape: clobbers, out, and the typed parameter list are the routine's contract, and they are checked, not decorative.

New here? · Why would a build refuse to produce a ROM?

In most toolchains a build fails only when it cannot understand you: a typo, a missing file, a line that is not valid. .emp adds a second reason. When a routine's contract and its instructions disagree, the assembler understands you perfectly; it just will not go along with it. It stops and names the routine.

Teaching example · not engine code

To feel the gap between a comment and a contract, take a made-up routine that promises to leave d3 untouched and then plainly does not:

proc Add_Two (d0: u16) clobbers(d1) preserves(d3) {
        move.w  d0, d1
        addq.w  #2, d1
        move.w  d1, d3          // stashes the result in d3
        rts
}

In plain assembly the preserves(d3) note would be a harmless lie: the routine writes d3 and never gives it back, but nothing would object, and a caller trusting the note would be quietly corrupted. Sigil objects. The fix is to tell the truth, clobbers(d1, d3), or to genuinely save and restore d3. Either way the header ends up matching the code, which is the whole point: the annotation is not allowed to disagree with the instructions.

The body, by contrast, holds no surprises. moveq, move.b, cmpi.b, bhs: these are 68000 instructions doing 68000 things, exactly as the CPU tracks teach them. The .full line ending in a colon is a local label, a branch target private to this routine (its leading dot marks it local). The // lines are comments. And the if DEBUG == 1 { } block is a build-time choice: those lines are included only in a debug build and vanish entirely from the plain one, a topic section 6 returns to.

So a single screen of .emp is written for three different readers at once, and the skill this page is really teaching is telling them apart. Some lines are instructions for the CPU to run. Some are promises for the checker to verify. Some are directions to the assembler about names, values, and what to include. The file walker below lets you click any line and see which is which.

Decision Brace blocks and one-level indentation, not label-and-column layout. Classic assembly leans on columns: a label starts at the left margin, instructions sit indented, and where one routine ends and the next begins is a matter of reading convention. .emp instead wraps each routine in explicit { } braces with an indented body, the way most modern languages do, so the boundaries are unambiguous and the assembler always knows exactly which lines belong to which routine. The honest cost is diff noise: introducing a brace-and-indent structure moves lines that a pure column layout would have left alone, and a programmer used to reading down a fixed column has a small new habit to build. The payoff is that a routine's extent, and so the exact span its contract governs, is something you can see rather than infer.

3 · Instructions are still instructions

Inside a routine body, 68000 code is 68000 code and Z80 code is Z80 code: the same mnemonics, the same operand order, the same sizes and flags as the instruction tracks teach. .emp adds no virtual instructions of its own, and a plain instruction line hides no secret code generation. What move.w d0, d1 does, and what it costs, you look up on the 68000: Moving Data page; what ld a, (hl) does you look up on the Z80 track. This page never re-teaches an instruction, and neither does the language.

The rule to carry, and it is a rule about spelling rather than a count: a line whose leading word is a CPU mnemonic assembles to that one instruction, and the only thing left open is its encoding width, if you left the size suffix off. A line whose leading word is a named .emp construct may emit several instructions, or choose among them, or emit nothing. You tell the two apart by the word at the front, and the constructs are a closed set you can learn once. Here are the ones you will actually meet in engine source:

  • assert.b / assert.w / assert.l (as in the ring buffer's assert.b d4, eq, #0) expands into real checking instructions only in a debug build; in the plain build it produces nothing at all.
  • invoke, the way the engine calls out to a game, expands to an absolute jsr when the game supplies a routine and to nothing when it does not.
  • jbra and jbsr pick a reaching encoding for you, which is the whole of the next section. Plain bra, bsr and the conditional branches written without a size suffix are chosen for you too, over a smaller two-step ladder; on the Z80 the same goes for an unsized jr, which the assembler may widen to a jp.
  • with ctx { } wraps its body in a context's acquire and release instructions, so a block that looks like plain code carries a splice at each end. The next page is where this one earns its keep.
  • mul_const and mul_bounded emit a multiply as a shift-and-add chain or as a real mulu, whichever the cost model prefers for that constant.
  • raise_error and raise_exception expand into the fatal-error blob; todo! and unreachable! each assemble to the 68000 ILLEGAL word, so an unfinished routine builds and stops at the hole rather than running past it.
  • dc lays down data rather than code, and pad_to_cycles emits however many nops a timing target needs.
  • assume_some emits nothing at all: it is a typing assertion the checker reads, costing zero bytes and zero cycles.
  • asm { } splices a block of code built at build time into the instruction stream.

What none of them do is hide. Every one is a word you can search for, and none of them is spelled like a CPU instruction, so the property that actually matters holds: reading a body, you can tell which lines are the machine and which are the language, by eye, without a lookup.

Away from those words, a body is literal. The clearest case is a routine that is nothing but instructions and one contract header. This is the engine's sine and cosine lookup: its header promises it clobbers nothing and returns results in d0 and d1, and its body is seven plain 68000 instructions.

pub proc GetSineCosine (d0: Angle) clobbers() out(d0, d1) {
        andi.w  #$FF, d0
        add.w   d0, d0
        addi.w  #$40*2, d0
        move.w  Sine_Table(pc,d0.w), d1
        subi.w  #$40*2, d0
        move.w  Sine_Table(pc,d0.w), d0
        rts
}
engine/system/math.emp:21-29 (comments omitted)

Read the body and it is entirely familiar: mask the angle to a byte, double it to index a word table, add a quarter-turn to reach the cosine entry, load it, subtract the quarter-turn back, load the sine, return. The only .emp-specific mark is Angle on the parameter, a domain type layered over the plain u8 so the checker can catch you passing something that is not an angle. It changes no bytes and costs no cycles; the type layer is its own later page. Strip the header and you have assembly that would run on any 68000.

New here? · Why does "the language adds no instructions" matter so much?

On a 1990s console, cycles and bytes are scarce and every one is accounted for. A language that quietly turned one line of yours into three instructions, or slipped in a helper call you did not write, would make it impossible to reason about timing, and timing is the whole game on this hardware. An NTSC frame is about 128,000 68000 cycles, but the VBlank window, the only stretch in which bulk video work is safe, is roughly 18,000 of them, and the engine must fit its video work inside that. So the promise that an instruction line is exactly the instruction you wrote is not a stylistic nicety, it is what lets a programmer keep predicting the machine exactly. Code is still generated for you, by the named constructs listed above, but only where you wrote one of their names: no plain instruction line grows a byte behind your back.

4 · Write the intent, not the bytes: jbra and jbsr

The 68000 gives you several ways to reach a routine, and they differ in size and in how far they carry. A short branch is two bytes but reaches only a little way; the next size up is four bytes and reaches much further, though still not across an arbitrary ROM. In plain assembly you choose, by writing bra.s or bra.w, and if you guess "short" for a target that turns out too far away, the assembler rejects it and you go back and change the letter. That round trip is pure bookkeeping, and it is exactly the sort of thing a tool should do for you.

So .emp gives you jbra (an auto-reaching jump) and jbsr (an auto-reaching call). You write your intent, "go to this routine", and the assembler emits the shortest encoding that actually reaches it, widening only as far as it must. Here is a real tail call using jbra: this routine's last act is to jump to another one, letting that one's return carry control home.

pub proc Sound_Ping (d0: u16) clobbers(a0) preserves(sr.mask) {
        lea     PING_SLOT, a0
        jbra    Sound_PostByte
}
engine/sound/sound_api.emp:160-163

What the assembler is choosing among is a ladder of four rungs, in this order, and it takes the first one that reaches. The order is by size, with one deliberate tie broken toward the position-independent form:

RungEncodingBytesReaches
0BRA.s / BSR.s2 a displacement of -128 to +127 from the PC. A displacement of 0 is excluded: that encoding means something else.
1BRA.w / BSR.w4 a displacement of -32768 to +32767 from the PC. This is why a word branch cannot reach an arbitrary point in a multi-megabyte ROM: the reach is 32 KB either side of where you are, not of where the ROM starts.
2JMP / JSR with a word address4 targets in $000000 to $007FFF or $FF8000 to $FFFFFF, the two ranges a sign-extended 16-bit address can name. Same size as rung 1 but ranked after it, because a PC-relative branch survives the code moving.
3JMP / JSR with a long address6 anywhere. This rung always reaches.

Two consequences worth keeping. Because rung 3 always reaches, jbra and jbsr can never fail to reach a target: there is no case where you are sent back to widen something by hand. And there is no BRA.l in the list because the 68000 does not have one; this is a plain 68000, not one of its later relatives, and the long-distance rungs are jumps rather than branches for exactly that reason.

New here? · Why let the assembler choose the branch size?

The target is the same routine either way; the only question is how many bytes the jump itself needs, so the choice is about encoding, not about what the program does. The assembler already knows where everything lands, so it can pick the smallest form that reaches.

It has to re-pick, too, and that is the subtle part. Widening one branch from two bytes to four pushes everything after it along, which can put some other branch out of reach. So the assembler settles the whole file by repetition: it starts with everything at its smallest, widens whatever no longer reaches, and goes round again until nothing changes. Encodings only ever grow in that process, never shrink back, which is what guarantees it stops.

Now the payoff, and it is about reading, not writing. Because jbra and jbsr cover every ordinary jump and call, the plain instructions jmp and jsr are reserved for one specific thing: a dispatch whose target is computed at run time, not known when the code is written. So when you are reading engine code and you see a bare jmp or jsr, that is a signal: something dynamic is happening here, a jump through a register or a table, not a plain call to a named routine.

And even those dynamic jumps can carry a type. A computed call that dispatches to a routine is annotated with the kind of thing it is allowed to land on, written as a contract type, so the checker still has something to hold it to. Here the engine dispatches to whatever the current game state routine is:

        movea.l Game_State, a0
        jsr     (a0) as GameState       // computed dispatch (bare jsr by the jbra/jbsr rule)
        jbra    GameLoop
engine/system/game_loop.emp:42-44

The jbra GameLoop right after the dispatch is the loop closing on itself with an auto-reaching jump. How that typing is enforced, and the enumerated form that lets the checker cost every branch of a jump table, are later pages; for reading, name it and move on.

Decision Reserve bare jmp and jsr for computed targets, so the mnemonic carries meaning. The auto-reaching pair could have been optional sugar sitting alongside the hand-sized branches. The language instead makes them the normal way to reach a named routine, which frees jmp and jsr to mean only "the destination is computed". That is a readability contract: a reader who sees jsr (a0) knows without checking that a dynamic dispatch is happening, and a reader who sees jbsr Foo knows the target is a fixed, named routine. The honest cost is one more idiom to learn and the loss of hand-picking an encoding in the rare case you would want to; the payoff is that the distinction between a plain call and a dynamic one is visible in the verb itself. The 68000: Flow page tells the underlying story of how branch reach and sizing work.
Gotcha When you meet a bare jmp/jsr, expect a register or an indexed table as its operand and an as SomeType annotation naming what it may land on. If you are hunting for where a routine is called from, searching for jbsr and jbra finds the static calls; the bare forms are the computed ones.

This is a rule about the source, not about the ROM. Rungs 2 and 3 of the ladder above are literally JMP and JSR instructions, so a disassembly of the finished cartridge is full of jumps to fixed addresses that were jbra and jbsr in .emp. Reading engine source, a bare jmp means a computed target. Reading a disassembly, it means nothing of the kind, and you have to look at the operand.

5 · Where code goes

Here is something a .emp file never contains: its own ROM address. No module says "assemble me at $1A200". A module declares only what it is, a set of routines and data belonging to a named section, and a separate placement map, one per game, decides where each section sits in the finished ROM. The module engine.objects.rings in rings line from section 2 named the section (rings); the map is what turns that name into a location.

Labels still become symbols. When the map has placed a section, every label in it resolves to a real address, and that is how a jbra or a data reference finds its target. What is gone is the programmer writing the address down. You name things and refer to them by name; the map, and the assembler resolving against it, supply the numbers.

Decision One placement authority: the map, never the source. Layout could have lived in the files, each declaring its own origin, the way traditional assembly does. Putting it all in one map instead deletes a whole class of bug at the root. When many files each name their own address, two can silently claim overlapping ROM, a gap can open between them unnoticed, and moving one region means hand-editing address arithmetic in several places. With a single map owning every placement, an overlap or a gap is something one authority can see and reject, and a module is free to move without touching a number. The honest cost is indirection: to answer "where does this end up in the ROM?" you read the map, not the file, so the file alone no longer tells you its own address.
New here? · Why keep placement out of the file at all?

Think of the difference between everyone in an office picking their own desk by writing their name on a spot, versus one seating chart that assigns every desk. In the first world, two people can choose the same spot and nobody notices until they both show up; rearranging one team means renegotiating with everyone nearby. In the second, one chart is responsible for the whole floor, and it simply cannot double-book a desk, because a single authority is placing them all.

6 · One source, several ROMs

The ring buffer had a block guarded by if DEBUG == 1. That is the last kind of line to recognize, and it is how one set of source files produces more than one ROM. A build has a shape, most simply plain or debug, and a comptime conditional decides, at build time, whether the code inside it is part of the ROM being built. In the plain shape, the debug block is not disabled at run time; it is never assembled at all, so the plain ROM does not carry a single one of its bytes.

        if DEBUG == 1 { move.l #SPIN_WATCHDOG_LIMIT, d1 }   // DEBUG watchdog budget
engine/sound/sound_api.emp:137

In a debug build this line loads a watchdog limit into d1; in a plain build it is as if the line was never written. This is why a debug assertion like the ring buffer's costs the release ROM nothing: DEBUG is a value the build chooses, the if is resolved while assembling, and only the chosen shape's bytes are emitted. The word is comptime, for "compile time", meaning work that happens while building rather than while the game runs. The full story of build-time values and code selection is the planned Comptime page; for reading, an if DEBUG == 1 { } block is simply "these lines exist only in the debug shape".

New here? · What is a debug build, and why have more than one ROM?

While developing a game you want extra help: checks that catch mistakes, on-screen counters, hooks that let you jump around. All of that costs bytes and cycles, and none of it belongs in the cartridge you ship. The classic answer is to keep two versions of the code, which drift apart the moment someone edits one and forgets the other.

.emp's answer is one set of source files that can be built in different shapes. The debug-only code lives right next to the code it checks, wrapped so the build can include or drop it, and the release shape comes out with none of it. You never maintain two copies.

Be precise about what that buys, because it is narrower than it sounds. What is guaranteed is that code inside a comptime if DEBUG == 1 { } is not assembled in the plain shape, so the bytes genuinely are not there. What is not guaranteed is that all the debug-ish code is inside such a gate: nothing checks that, and the @scaffolding("reason") marker some routines carry is a note for humans that enforces nothing. Nor does the release ROM contain no diagnostics at all. Aeon's release build deliberately ships the MD Debugger island and its symbol appendix, so that a player's crash is reportable; what it drops is the equipment, meaning the assertions, the sound-debug hotkeys and mirror, the boot autoplay, the self-tests. And the build shape is a property of the build, not of the file on the shelf: nothing stops someone handing out the debug ROM by mistake.

7 · How to keep reading

You can now read any .emp line on this wiki and say what it is. A module and its use imports open the file. const lines name build-time values. A proc header carries the routine's contract, the promises the checker holds it to. Instruction lines are ordinary 68000 or Z80. jbra and jbsr are auto-reaching jumps and calls, while a bare jmp or jsr means a computed target. local labels are private branch targets, // lines are comments, and if DEBUG == 1 { } blocks belong to a particular build shape. Placement is the map's job, never the file's.

The one thing this page deliberately left shallow is the contracts themselves: what clobbers, preserves, out and requires each promise in full, how far the checker proves each one, and the real defects it has caught in shipping engine code. That is the next page, and it is the heart of the language.
