68000 Assembly

Instructions: System

These are the instructions that talk to the machine rather than to your data: halting the CPU, resetting the hardware, switching between privilege levels, and deliberately causing an exception. One of them is in every Genesis game ever written. Most of the rest appear zero times in any of the disassemblies, and that is not a gap in the games, it is a fact about what a cartridge console is. This page is the last of the 68000 instruction reference, and it is mostly an argument: you learn what a games console actually is by seeing which instructions it makes pointless.

1 · The one you will actually meet

Almost every instruction on this page is one you will never see in a Genesis game. This first one is the opposite: it is in all of them. Counted across seven codebases, move to or from the status register appears 4 times in Sonic 1, 47 in Sonic 2, 111 in Sonic 3 and Knuckles, 10 in the Sonic Clean Engine, 31 in the Sonic Hack engine, 23 in Aeon, and 49 in MarkeyJester's homebrew Mega Drive operating system. It is ordinary, everyday code, and it is worth understanding before anything else here.

What it touches is the status register, and that register has two halves that behave completely differently. You already know the low half: it is the condition codes, X N Z V C, the flags that cmp and add set and that beq reads. Every earlier page on this track has been quietly working with it. The high half you have not met, and it is where this page lives.

New here? · What does privileged mean, and does it matter on a cartridge?

The 68000 runs in one of two states. In supervisor mode every instruction is allowed. In user mode a handful of instructions are refused, and attempting one raises an exception instead of executing.

The idea is that an operating system runs in the privileged state and the programs it hosts run in the restricted one, so a misbehaving program cannot turn off interrupts or halt the machine. A Genesis cartridge has no operating system and boots straight into supervisor mode, so it never leaves it. Every privileged instruction on this page is therefore simply available, all the time.

That does not make the distinction invisible. Assemblers still know which instructions are privileged and will say so: point one at AS and it prints warning: privileged instruction. It is a warning and not an error, the ROM still builds, and on this machine the warning is telling you about a restriction that does not apply.

The three instructions in this section are the ones that read and write those two halves. They are also where the 68000 gets asymmetric in a way worth knowing about, because the two halves are not equally protected.

Teach

Why this page states no cycle counts. Every other instruction page on this track gives you timings. This one does not, and that is deliberate rather than an oversight: the sources we trust for 68000 timing do not cover these instructions, so any number here would be one we could not stand behind. Byte sizes are given, because those follow directly from how the instruction is encoded. It matters less than it would elsewhere, because nothing on this page sits on a hot path. That is the whole point of the page.

Why a CPU has two privilege levels at all, and why this console never uses the feature

The 68000 has two modes because it was built for machines where the CPU is shared. On a workstation or an Amiga, an operating system is in charge and the programs it runs are not trusted: one of them crashing, or writing over another one's memory, or switching interrupts off and never switching them back on, must not be able to take the machine down. So the CPU offers a lower gear. In user mode the dangerous instructions are simply refused, and refusing them raises an exception, which hands control back to the operating system, which gets to decide what to do about it.

That is the entire purpose of the S bit in the status register, and of the separate user stack pointer, and of the word "privileged" appearing on half the instructions on this page. It is a mechanism for not trusting the program that is running.

A Genesis cartridge is the trusted program. It boots in supervisor mode, it is the only program on the machine, and there is nothing above it to hand control back to. So it stays in supervisor mode from power-on until the console is switched off, every instruction is permitted to it at all times, and the second gear is never engaged. You can watch this in the explorer above: clear the S bit and the CPU is in user mode, which on this hardware is a state nothing ever deliberately enters.

This is worth holding on to, because it explains most of the rest of the page in advance. An instruction whose job is to report a problem upwards has nowhere to report to. An instruction that asks permission has nobody to ask. The privilege system is not broken here and it is not unused because anyone dislikes it. There is simply only one program, and it is already trusted.

MOVE SR Move Status Register MOVE SR,<ea>  |  MOVE <ea>,SR  (word only)

Flags Xsee note Nsee note Zsee note Vsee note Csee note Reading the SR leaves the flags alone. WRITING it replaces all five, because the flags live inside the thing you just overwrote
Cost 2 bytes 4 bytes with an immediate register or immediate forms; a memory destination adds its own address words.

Reading is the safe direction and the common one. move sr,d0 copies the whole 16-bit register into a data register so you can put it back later, which is what code does when it wants to change one thing about the machine's state and then undo it.

Writing is privileged, and this is the single most useful thing on this page to actually remember: move #$2700,sr is how Genesis code turns interrupts off, and move #$2000,sr is how it turns them back on. That is what those 111 uses in Sonic 3 and Knuckles mostly are. When you see either line in a disassembly, read it as "no interruptions from here" and "interruptions allowed again".

Here it is at the very end of Sonic 2's boot sequence, in code Sega distributed rather than anything a hacker wrote. The line before it clears every register; the line after it jumps into the game:

	move.w	d0,(a2)
	movem.l	(a6),d0-a6	; clear all registers
	move	#$2700,sr	; set the sr
s2disasm/s2.asm:271-273
Gotcha On a 68000, reading the SR is not privileged, which looks like an oversight and is one. User code can read the supervisor bit and find out whether it is being supervised. Motorola closed that hole on the 68010 by making MOVE from SR privileged too, which then created a new problem and a new instruction; see MOVE to CCR below.
Encoding

Two separate encodings that look like one instruction. Reading is 0100 0000 11 mmm rrr and writing is 0100 0110 11 mmm rrr; the trailing pair is the other operand. move sr,d0 is 40C0, move sr,(a0) is 40D0, and move #$2700,sr is 46FC 2700, the second word being the immediate.

There is no size field in either, because both are always word operations. That is why writing move.w or plain move makes no difference here, and why move.b has nothing to encode into.

MOVE to CCR Move to Condition Codes MOVE <ea>,CCR  (word source, low byte used)

Flags Xwritten Nwritten Zwritten Vwritten Cwritten All five come straight from the low byte of the source. This instruction exists to set flags without computing anything
Cost 2 bytes 4 bytes with an immediate writes only the low byte of the status register, so it is not privileged.

This is the unprivileged way to write flags: it touches the user half of the status register and leaves the system half alone, so user code is allowed to do it. Games use it to restore flags they saved earlier, and the best example in any of the disassemblies is the Kosinski decompressor, which has to carry a carry bit across code that would destroy it:

	move.b	(a0)+,(sp)
	move.w	(sp),d5	; get next description field if needed
	moveq	#$F,d4	; reset bit counter

.chkbit:
	move	d6,ccr
	bcc.s	Kos_RLE
s2disasm/s2.asm:2596-2602

Read the pairing rather than the single line: somewhere earlier this routine did move sr,d6 to stash the flags, and here it does move d6,ccr to put them back, and only then does bcc ask its question. The instruction that answers is three lines away from the instruction that set up the answer. That is a protocol, not a statement.

Gotcha There is no MOVE from CCR on a 68000. You can write the condition codes on their own, but you cannot read them on their own: to read them you must read the whole status register, and on later CPUs that became privileged. Motorola noticed and added the missing instruction on the 68010, and the reason is worth reading in full because it explains both halves of the asymmetry: making MOVE from SR privileged closed the loophole above, but it also left user code with no way to see its own flags, so MOVE from CCR was invented to give that back. Our disassemblies show the asymmetry without needing the manual: across Sonic 1, 2 and 3 and Knuckles there are 15 writes to CCR and not one read, because a read would not assemble.
Encoding

0100 0100 11 mmm rrr, one bit pattern away from MOVE to SR, which is the encoding admitting they are the same operation aimed at different halves. move d0,ccr is 44C0.

Note what is missing: there is no matching read form. The 68000 has no move ccr,<ea> encoding at all, which is why reading the condition codes on this chip means reading the whole status register and ignoring the top half.

MOVE USP Move User Stack Pointer MOVE.l An,USP  |  MOVE.l USP,An  (privileged)

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. Moves an address, touches no flags
Cost 2 bytes always; both directions.

The 68000 has two stack pointers, and a7 means whichever one is currently in force: the supervisor stack pointer while the S bit is set, the user stack pointer while it is clear. Since a Genesis game never leaves supervisor mode, it never uses the user stack pointer for anything, and the only way to touch it at all is this instruction.

Which makes what the disassemblies contain almost funny. There are four uses of MOVE USP across every codebase measured, and they are all the same line:

	move.l	a6,usp	; set usp to $0
s2disasm/s2.asm:218

The identical instruction, with the identical comment, appears in Sonic 1, in Sonic 2, in both Sonic 3 and Knuckles trees, and in the Sonic Hack engine. It is boot-time hygiene inherited by copying: a6 holds zero at that moment, so the line parks the unused stack pointer at address 0 and nothing ever reads it again. Every single use is a write; nobody has ever needed to read it back.

Encoding

0100 1110 0110 d rrr. Only four bits carry information: the direction bit d and the address register. move a0,usp is 4E60 and move usp,a1 is 4E69.

The operand can only ever be an address register, so there is no mode field, and the user stack pointer is not named at all: it is implied by the opcode.

2 · What the rest of this page is about

Everything from here on is an instruction that the 68000 offers and that Genesis games, almost without exception, refuse. Rather than assert that, here it is counted. Seven codebases: the three original Sonic disassemblies, the Sonic Clean Engine and the Sonic Hack engine that descend from them, Aeon, and MarkeyJester's homebrew Mega Drive operating system, which is on the list precisely because an operating system is the one thing on this platform that would have reason to use these.

Teach

Read the zeros twice. The obvious reading is "these instructions are useless", and that is wrong. Every one of them is useful, on the machine it was designed for. The 68000 went into workstations and Amigas and Macintoshes, where an operating system shares one CPU between programs that do not trust each other, and where a compiler emits code for functions it has never seen. On that machine LINK and CHK and TRAP are ordinary.

A Genesis cartridge is the opposite of that machine. It owns every byte of memory, it is the only program running, there is nothing to ask permission from and nothing to protect itself against, and it was written by a human who knew exactly where everything was. The zeros are not a judgement on the instructions. They are a description of the console.

Two of those zeros come with an honesty warning, and it is worth reading before section 3 makes an argument out of them. All seven codebases here are Sonic-family or homebrew, which means they share habits. A row of zeros across seven relatives is weaker evidence than it looks. Section 3 tests one of these claims against a completely unrelated 1992 commercial game, and the claim does not entirely survive.

3 · Nobody here needs scratch paper

LINK and UNLK exist to give a routine a private block of memory that lasts exactly as long as the routine does. Ask for sixteen bytes on the way in, use them, hand them back on the way out. If you have written in C, this is where your local variables live, and a compiler emits these two instructions around almost every function it compiles.

New here? · What is a stack frame, and why would a routine want one?

A stack frame is scratch space. A routine that needs a few temporary values, and has run out of registers to keep them in, can move the stack pointer down by some number of bytes and use the gap as private storage until it returns.

This is how compiled languages give you local variables. Every call to a C function that declares locals opens a frame on entry and drops it on exit, which is why recursion works: each call gets its own copy of everything, stacked on top of the last.

Hand-written Genesis assembly almost never wants this, because the alternatives are cheaper. Sixteen registers is a lot when one routine has the machine to itself, and anything that needs to outlive a call goes in a fixed location in work RAM, which costs nothing to reach. A frame buys you re-entrancy, and re-entrancy is a problem this code does not have.

Zero uses across all seven codebases. So does a Genesis game just not need temporary memory?

New here? · What is the machine doing while STOP is stopped?

Nothing, and that is the point. The CPU stops fetching instructions entirely and waits, drawing less power, until an interrupt arrives at a level its mask allows through. Then it resumes at the instruction after the STOP.

What makes it useful rather than a hang is that the mask and the halt are set by the same instruction. Written as two, there would be a window between them where an interrupt could arrive before the CPU was ready to wait for it, and the machine would sleep through the very thing that was meant to wake it.

A game has no reason to want this: there is always more to do before the next frame, and a console with nothing to do just draws the same picture again.

That was the conclusion, until the claim got tested against a game with no relationship to Sonic at all. Thunder Force IV, by Technosoft, shipped in 1992, the same year as Sonic 2. It uses stack frames throughout: thirteen of them, with sizes running from 16 bytes up to 256.

        movem.l    d2-d3/a0-a1/a6, -(a7)
        link.w     a6, #$ff80
        movea.l    a7, a0
        movea.l    a0, a1
        lea.l      $14cbc.l, a2
        moveq      #$7, d2
        move.w     (a2)+, d3
        add.w      d1, d3
        move.w     d3, (a1)+
        move.l     (a2)+, (a1)+
        move.w     (a2)+, d3
        add.w      d0, d3
        move.w     d3, (a1)+
        dbra       d2, $c9ec
        move.w     #$f800, d0
        move.w     #$20, d1
        bsr.w      $1219e
        unlk       a6
        movem.l    (a7)+, d2-d3/a0-a1/a6
        rts
thunderforce4_disasm/code/disasm.asm:9926-9945

Save the registers, link to carve off 128 bytes, do the work, unlk to give them back, restore the registers, return. That is a textbook frame, and it means the flat claim was simply wrong: a Genesis game absolutely can use stack frames, and one of the best-regarded shooters on the console does.

Honesty The Thunder Force IV code on this page is held to a lower standard of evidence than everything else here, and you should know which is which. The Sonic disassemblies are hand-maintained: humans have labelled and commented them for years. The Thunder Force IV listing is a first-pass automated disassembly with machine-generated labels, which is why the code above says bsr.w $1219e instead of a routine name. An automated pass also mistakes data for instructions, so isolated findings from it cannot be trusted.

What makes this finding safe is that it is not isolated: thirteen LINKs and thirteen UNLKs that pair up, frame sizes that fall on sensible round numbers, and a prologue and epilogue in the right order around a body that reads as deliberate code. Data misread as instructions does not produce that. Take the pattern as solid and the exact line numbers as provisional.
Teach

So what is the real difference? Not the era, and not the console. Look at what Thunder Force IV does with the frame: it points a0 at the fresh 128 bytes and streams a list into them, builds something there, uses it, and throws it away. It wants memory with a lifetime.

The Sonic engines never want that, because every buffer they use already exists at a fixed address that was decided once and written down. If you own the whole machine and have already mapped every byte of it, you never need to ask for scratch space; you just use the scratch space you named years ago. The question LINK answers is "may I have some memory for a moment", and a program that owns everything never has to ask.

LINK Link and Allocate LINK An,#displacement

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. Pure bookkeeping on the stack pointer; no flags move
Cost 4 bytes the displacement is a word, so it always costs an extension word.

Three things happen, in this order. The address register you name is pushed onto the stack. The stack pointer is then copied into that register. Finally the displacement is added to the stack pointer, and because you want to allocate, the displacement you write is negative: #$ff80 is -128, so the stack pointer drops 128 bytes and those bytes are now yours.

The register you named is now a frame pointer, sitting at a fixed spot in the middle of the arrangement so you can reach your locals at known offsets from it no matter what else you push afterwards.

Gotcha Thunder Force IV never uses the frame pointer. Across all thirteen of its frames there is not one reference to a6 as a base register: it takes the 128 bytes and reaches them through a7 instead, and lets the frame pointer it just set up go unused. So it is not using LINK the way a compiler would, and this is not compiled C. It is using LINK as a two-instruction way to say "move the stack pointer down by 128 and remember where it was", which is the useful half.

This is the same joke as TAS in section 5, and it is worth noticing twice: the instruction is kept for a side effect, and the thing it was named for is discarded.
Encoding

0100 1110 0101 0 rrr then a 16-bit signed displacement. link a6,#-8 is 4E56 FFF8, the second word being -8. The displacement is always present and always a word, which is why LINK is four bytes even when the frame is small, and why the displacement is normally negative: it moves the stack pointer DOWN to make room.

UNLK Unlink UNLK An

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. No flags
Cost 2 bytes always.

Exactly LINK backwards, and only two steps because it does not need the displacement: copy the frame pointer into the stack pointer, which discards the whole frame in one move however big it was, then pop the saved register back. The frame is gone and the stack looks like it did before.

Never read one without the other. A LINK with no matching UNLK leaks the stack a little on every call, and since the return address is on that same stack, a routine that gets this wrong does not fail politely. In Thunder Force IV they match exactly, thirteen and thirteen.

Encoding

0100 1110 0101 1 rrr. The same word as LINK with one bit flipped, and no displacement, because UNLK does not need to be told the frame size: it recovers the old stack pointer from the frame itself. unlk a6 is 4E5E, against LINK's 4E56.

STOP Load Status Register and Stop STOP #immediate  (privileged)

Flags Xwritten Nwritten Zwritten Vwritten Cwritten The immediate is written into the WHOLE status register, so it sets the flags as a side effect of setting the interrupt mask
Cost 4 bytes opcode plus the immediate word.

STOP loads the immediate into the status register and then halts the processor. It stays halted until an interrupt arrives that the new interrupt mask permits, and then it resumes at the next instruction. Both halves are one instruction on purpose: if you set the mask first and halted second, an interrupt could arrive in the gap.

Zero uses in all seven codebases here. But Thunder Force IV uses it seven times, and this is what it looks like:

        move.w     #$400, $f100.w
        stop       #$2500
        bsr.w      $1956
thunderforce4_disasm/code/disasm.asm:178-180

Try $2500 in the status-register explorer and it decodes as supervisor on, mask 5. Mask 5 blocks interrupt levels 1 to 5 and permits 6 and 7, and VBlank on this hardware is level 6. So that line means: stop the CPU dead until the next frame begins.

The Sonic engines want the same thing and get it the other way, by spinning in a loop until a VBlank handler changes a flag in RAM. Both wait for the frame. One of them burns every cycle of the wait, and one of them stops the clock. Same goal, and the instruction that does it in one line is the one that appears zero times in every Sonic codebase.

Encoding

0100 1110 0111 0010 then the word to load into the status register. stop #$2700 is 4E72 2700. The immediate is not optional: STOP always sets SR and halts in one act, which is what makes it safe to use at all, since setting the mask and halting as two instructions would leave a window between them.

4 · No operating system to complain to

Section 3's silence turned out to be about a habit, and a game written differently broke it. This section's silence is a different kind, and it holds. These four instructions are zero in every codebase measured, including Thunder Force IV, which just refuted the other claim, and including a homebrew operating system that had every reason to want them.

New here? · What is an operating system actually doing that a game does not?

An operating system shares one machine between programs that do not trust each other. That job creates the needs the instructions in this section were designed for: a program must be able to ask the system for something without knowing where the system lives, and the system must be able to stop a program that misbehaves.

A Genesis cartridge is the opposite situation in every respect. One program owns the whole machine, it was all written together, it knows every address in itself, and there is nobody to report a problem to. Asking for a service is just jsr to a label you already know.

So the instructions are not badly designed and they are not broken here. They answer a question this platform does not ask.

They share a shape: each one is a way of reporting a problem to somebody else. And on a cartridge there is no somebody else.

New here? · If a trap is an error, why would you cause one on purpose?

Because "exception" on the 68000 does not mean "mistake". It means a forced detour: the CPU stops, looks up an address in the vector table, and jumps there. What that detour is FOR is entirely up to whoever filled in the table.

On a machine with an operating system, a deliberate exception is how a program asks for service. The program cannot call the system directly, so it raises one on purpose, and the handler on the other side reads what was wanted and does it. The exception is the doorbell.

On a cartridge there is nobody on the other side of the door, so a deliberate exception has only one honest use left: crashing on purpose, at a moment you choose, so the crash handler can tell you where you were. That is what the engines here do with the ones they use.

CHK Check Register Against Bounds CHK <ea>,Dn

Flags Xunaff. Nundef. Zundef. Vundef. Cundef. N is defined only in the two cases that trap: set if the register is negative, cleared if it exceeds the bound. After a CHK that passes, and that is the only case where your next instruction runs, all five are undefined
Cost 2 bytes plus any words the source operand needs.

CHK compares a data register against an upper bound and, if the register is negative or greater than the bound, raises an exception instead of continuing. It is an array bounds check in one instruction, and it exists because the 68000 was designed with high-level languages in mind: a compiler for a language that checks its subscripts can emit CHK and let the CPU do the comparing.

Nobody on this platform uses it, and the reason is not that Genesis programmers were careless about array bounds. It is that CHK's response to a bad index is to raise an exception, and an exception is only useful if something is waiting to catch it and do something sensible. On a cartridge, the thing waiting is a crash handler whose entire job is to stop the game and print an error. A programmer who already knows the index is fine does not want the check; a programmer who is not sure would rather cmp and branch and handle it, because then the handling is theirs.

Encoding

0100 rrr 110 mmm rrr. The first rrr is the data register being checked, 110 marks the word size, and the trailing pair is the upper bound's operand. chk d1,d0 is 4181 and chk (a0),d2 is 4590.

The size field only ever holds 110 on a 68000, since the word form is the only one this chip has; the long form arrived with the 68020.

TRAPV Trap on Overflow TRAPV

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. Reads V and changes nothing
Cost 2 bytes no operands at all.

One job: if the V flag is set, raise an exception; otherwise do nothing and carry on. It is the overflow equivalent of CHK, meant to sit after arithmetic in a language that promises to notice when a sum does not fit.

Zero uses, for the same reason as CHK plus a sharper one. Genesis code does not merely tolerate overflow, it relies on it: angles wrap around a byte because 256 units is exactly one revolution, and counters are allowed to roll over because the roll is the behaviour you wanted. An instruction whose whole purpose is to complain about wrapping is not much use in a program built on wrapping.

Encoding

0100 1110 0111 0110, and that is the entire instruction: 4E76. No operands, no fields. It takes the exception if V is set and does nothing at all if it is not.

RESET Reset External Devices RESET  (privileged)

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. Touches the outside world, not the CPU's own state
Cost 2 bytes no operands.

RESET asserts the CPU's reset line, which is wired to the other chips. It resets them and deliberately not itself: the 68000 keeps running, its registers intact, on the instruction after. It is the one instruction here whose effect is entirely outside the processor.

The clearest statement of why you will never see it comes from a 68000 textbook written in 1988, four years before Sonic 2, with no knowledge of this console at all:

Teach

"The RESET instruction can only be used in supervisor mode. When it is executed it asserts the hardware reset line. This normally causes all external devices to be reset. [...] Normally this instruction is executed by the operating system to ensure an initialized state for all external devices. Unless you are writing an operating system, you should never have need for this instruction."

Thomas P. Skinner, Assembly Language Programming for the 68000 Family, John Wiley and Sons, 1988.

That is the whole argument of this page in one sentence, made by somebody who was not making it. A Genesis game boots the VDP and the sound chips itself, one register at a time, because it knows exactly which state it wants them in. Pulsing a line that resets all of them to their defaults is a blunter tool than anything a game needs, and it would undo work the game had just done.

Encoding

0100 1110 0111 0000, or 4E70. No operands: it asserts the processor's reset line and nothing else, so there is nothing to encode.

ILLEGAL Take Illegal Instruction Trap ILLEGAL

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. The exception saves them; the instruction itself changes nothing
Cost 2 bytes the fixed opcode word $4AFC.

An instruction whose defined behaviour is to be invalid. The 68000 reserves the bit pattern $4AFC, guarantees it will never mean anything, and takes the illegal-instruction exception when it meets one. It exists so a program can crash on purpose, at a spot it chose, rather than waiting to crash by accident somewhere it did not.

One use across everything measured, and fittingly it is in the operating system rather than in any game. What happens after it, meaning what the CPU pushes on the stack and how a handler reads it back to tell you where you died, is the subject of its own page and not this one.

Encoding

0100 1010 1111 1100, or 4AFC. This is a real, defined opcode whose defined behaviour is to take the illegal-instruction exception, which is what makes it different from an arbitrary invalid word: it is guaranteed to keep behaving this way on every 68000, so code can rely on it.

5 · The two that arrived late

The last two are different from everything above. They are not absent from the Genesis; they are absent from the 1990s. Neither appears in any Sega-era disassembly, and both turn up in engines written by hobbyists two decades later, each solving one specific problem. And in both cases the instruction is being used for something other than the thing it is named after.

New here? · Why does reading and writing in one instruction need to be special?

Suppose two processors share one byte of memory as a "someone is using this" flag. Each wants to read the flag, and if it is clear, set it and proceed.

Written as two instructions, a read and then a write, there is a gap in the middle. If the other processor reads the same byte during that gap, both see it clear, both set it, and both proceed, which is exactly what the flag existed to prevent. The gap does not have to be likely to be fatal; it only has to happen once.

A read-modify-write closes the gap by doing all of it as one indivisible act, holding the bus throughout so nothing can look in between. That is the whole purpose of TAS, and it is why it is the only instruction of its kind the 68000 has.

TAS Test and Set TAS <ea>  (byte only)

Flags Xunaff. Nset Zset Vclear Cclear N and Z come from the byte's value BEFORE the set, which is the whole idea: you learn what it was and change it in one go
Cost 2 bytes on a data register; a memory operand adds its address words.

Start with what it does, because that is all you need to read the code below. TAS looks at one byte, sets N and Z from the value it found, and then sets that byte's top bit to 1. Two things in one instruction: you find out what the bit was, and you make it 1.

Why it exists is a story about a machine this is not. If two processors share memory, they need a way to agree on who owns something, and the danger is both checking at the same moment, both finding it free, and both taking it. TAS closes that gap by doing the checking and the claiming without letting go in between. A Genesis cartridge has one 68000 and nothing to negotiate with, so this purpose never comes up here at all.

And here is where it actually appears. Both the Sonic Hack engine and Aeon contain exactly one TAS, in the code that builds a VDP command word. In Aeon that is a compile-time function choosing which instruction to emit for the bit pattern it was handed:

comptime fn vcr_type(tr: int, reg: Reg) -> Code {
    let hi = tr & $FC
    if hi == $20 { return asm { tas.b   {reg} } }
    if hi != 0 { return asm { ori.w   #{hi << 2}, {reg} } }
    return asm { }
}
aeon/engine/vdp.emp:105-110

Read the two branches against each other. The second is the ordinary way to set some bits: ori.w with an immediate, which costs 4 bytes. The one above it fires when the bits needed happen to be exactly bit 7 of the low byte, and in that one case tas.b does the same job in 2 bytes, because setting bit 7 is what TAS does on its way past. Neither branch is a run-time test: whichever arm matches is the only one that puts any bytes in the ROM.

So the instruction survives here as a two-byte way to set a bit. The test half is ignored, the flags it sets are never read, and the multiprocessor problem it was invented for is not in the building.

Gotcha On a Mega Drive, TAS aimed at memory does not work. Sega documented this themselves, in the Genesis Software Development Manual Complement of July 1991: "The TAS command is not supported on the GENESIS. [...] If this command is issued, the test is executed and completed, but the setting will be ignored and not be written." The read happens; the write is thrown away.

Which makes the code above quietly lucky, or quietly wise. Its operand is a data register, and a register lives inside the CPU, so no outside chip gets a say and the bit really is set. The register form is the only form of TAS on this machine that does what the manual says it does. Note that the engines do not comment the line, so this is an observation about the code and not a claim about what the author was thinking.
Why the write is discarded, and which consoles differ

TAS is the 68000's only read-modify-write instruction, and it holds the bus for the read and the write together so nothing can slip between them. That indivisibility is the point, and it is also what the Genesis hardware does not handle.

The most detailed explanation available is by Nemesis, author of the Exodus emulator, in a source comment from 2011. His reading is that the address strobe stays asserted across the whole operation, and that the VDP works out its write-enable outputs once, at the start, when the operation still looks like a read, and never revisits them; so when the write half arrives, the lines that would tell the memory chips to store something are never raised. He marks this as inference rather than measurement, says "most likely", and notes the memory datasheets would need checking to confirm it. We have found nobody who has put a probe on the hardware to settle it, so treat it as the best available explanation and not as established fact.

The behaviour also differs by console revision. Emulator authors who test against hardware treat every model as discarding the write except one late Genesis 3 board revision, which performs it correctly. That sounds like an improvement and broke games: at least one commercial title, Gargoyles, depends on the write being thrown away, so it works on the machines of its era and misbehaves on the one that got TAS right. Emulators suppress the write by default for exactly this reason. A tidy correction to a documented defect, twelve years too late to be welcome.

Encoding

0100 1010 11 mmm rrr. It shares the 0100 1010 prefix with TST, and the 11 where TST's size field would be is what distinguishes it. tas d0 is 4AC0 and tas (a0) is 4AD0.

There is no size field because TAS is always a byte operation, and the missing size is the same slot ILLEGAL uses to mark itself: 4AFC is this pattern with the operand field set to an immediate, which no read-modify-write instruction could meaningfully use.

TRAP Trap TRAP #vector  (0 to 15)

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. The flags are saved as part of the status register and come back on return
Cost 2 bytes the vector number is packed into the opcode, so no extension word.

trap #n raises an exception on purpose. There are sixteen of them, numbered 0 to 15, and each has its own slot in the vector table: trap #0 goes through the slot at $80, trap #1 through $84, and so on. The CPU saves where it was, switches to supervisor mode, and jumps to whatever address it finds there.

That mechanism is how a program on a normal computer asks its operating system for something: cheap, two bytes, and the operating system decides what each number means. On a Genesis there is nothing to ask, so the sixteen slots have nothing to point at. Here is what Aeon does with all of them:

        dc.l    ErrorTrap, ErrorTrap, ErrorTrap, ErrorTrap   // $80-$8C: TRAP 0-3
        dc.l    ErrorTrap, ErrorTrap, ErrorTrap, ErrorTrap   // $90-$9C: TRAP 4-7
        dc.l    ErrorTrap, ErrorTrap, ErrorTrap, ErrorTrap   // $A0-$AC: TRAP 8-11
        dc.l    ErrorTrap, ErrorTrap, ErrorTrap, ErrorTrap   // $B0-$BC: TRAP 12-15
aeon/engine/system/vectors.emp:135-138

All sixteen go to the same crash handler (a build that ships without the debugger points the same sixteen at its own fault stop instead). The engine is not reserving them for later; it is declaring that arriving here at all is a bug. MarkeyJester's homebrew Mega Drive operating system, which has threads and a window manager and is the one program on this platform with a real reason to want a system call, contains zero TRAPs and reaches its services another way entirely.

And Aeon's single actual trap is not a system call either:

comptime fn jt_filler() -> Code {
    return 0..(sizeof(DMAEntry) - 4) / 2 |> fold(asm {}, |acc, _i| acc ++ asm { trap #0 })
}
// … the jump table's first slot …
    .jump_table:
    .slot_0:
        bra.w   .done                           // STRUCTURAL bra.w: slot 0 (queue empty) - the 4-byte head of the sizeof(DMAEntry)-wide slot
        jt_filler()
aeon/engine/system/dma_queue.emp:223-225, 282-285

This is a jump table. The first entry needs to fill the same number of bytes as every other entry, bra.w supplies four of them, and the remaining ten are five trap #0 instructions rather than five nops (the filler is generated: an entry is 14 bytes, four are spent on the branch, and each trap is two). Both would pad. The difference is what happens if the dispatch ever computes a wrong offset and lands in the middle of an entry: NOPs would let it slide quietly onward into whatever came next, and traps stop it dead and hand it to the crash handler.

So the only TRAP in the engine is a landmine for a bug, which is exactly what a vector table pointing sixteen slots at one crash handler already told you. The instruction designed for asking an operating system a question is being used here to make sure a certain kind of mistake cannot go unnoticed.

Encoding

0100 1110 0100 vvvv, where the low four bits are the vector number directly. trap #0 is 4E40 and trap #15 is 4E4F. Sixteen vectors is not a design decision made later: it is exactly what four bits hold.

6 · NOP, the exception that is everywhere

One instruction left, and it breaks the pattern completely: 38 uses in Sonic 1, 37 in Sonic 2, 102 in Sonic 3 and Knuckles, 71 in the homebrew operating system. NOP does nothing, which sounds like it should be the most pointless instruction on a page about pointless instructions, and instead it is the busiest.

New here? · How can an instruction that does nothing be worth having?

Because "nothing" is not the same as "no effect on the machine". A NOP still takes a fixed amount of time, still advances the program counter, and still occupies exactly two bytes. Those three properties are the three reasons to write one.

Time, when hardware needs a moment between two accesses and the CPU would otherwise get there too soon. Space, when something later has to sit at a particular address, or when a patch has to fill the room an instruction used to take. And as a placeholder, when code writes over itself at run time and needs somewhere valid to write into.

Doing nothing turns out to be three completely different jobs, and all three are in Sonic 2.

NOP No Operation NOP

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. Changes nothing at all. That is the specification, not a simplification
Cost 2 bytes and it spends time doing nothing, which is the point of the first use below.

NOP changes no register, no flag, and no memory. It advances the program counter and consumes time. Both of those nothings are useful.

Job one: spending time on purpose. Reading the controller needs a pause between telling the port what you want and reading back what it says, because the hardware needs a moment to settle. The pause is the instruction:

	move.b	#0,(a1)	; Poll controller data port
	nop
	nop
	move.b	(a1),d0	; Get controller port data (start/A)
s2disasm/s2.asm:1369-1372

Two NOPs of deliberate patience, and then the read. Delete them and the code is faster and wrong. This is the one place on this page where an instruction that does nothing is doing something no other instruction could.

Job two: filling the hole where code used to be. This one is a fossil, and the disassembly keeps it on display:

    if 0
	; Sonic 2 Beta 4 reveals that these were the original instructions.
	; The original source code may have been able to produce debug builds with this enabled.
	move.w	#$101,(Level_select_flag).w
	move.w	#$101,(Debug_mode_flag).w
    else
	nop
	nop
	nop
	nop
	nop
	nop
    endif

Two instructions that switched on level select and debug mode were removed before release. They were three words each, so six words had to be filled, and six NOPs is exactly what fills them. Count them: the arithmetic is visible. Somebody disabled a feature by writing over it with nothing, and because the replacement had to be the same size as the original, the shape of what was deleted is still legible in the shape of what replaced it. The comment above is a later reader working that out from a beta cartridge.

Job three, and the best one: a question nobody reads the answer to.

	lea	(Timer).w,a1
	cmpi.l	#(9<<(8*2))|(59<<(8*1))|(59<<(8*0)),(a1)+
	nop			; You can't get a Time Over in Debug Mode, so this branch is dummied-out
	addq.b	#1,-(a1)
s2disasm/s2.asm:87310-87313

The cmpi.l is still there. It still runs, every frame, comparing the timer against 9 minutes 59 seconds and 59 frames, and it still sets the flags according to the answer. What used to be on the next line was a branch that acted on those flags, and it is now a NOP. So the comparison happens and nobody asks.

Teach

That last one is the whole track in four lines, so it is worth saying plainly.

The machine has no idea what anything is for. The cmpi.l does not know it was supposed to be a Time Over check. It does not know the branch is gone, it cannot tell that its answer is now unread, and it will keep computing that answer forever without complaint. The flags it sets are correct. They are simply not a question anymore, because the only thing that made them a question was the instruction that used to follow.

This is the same fact that explains the whole page. LINK does not know it made a frame. TAS does not know it is for two processors. TRAP does not know it is for asking an operating system. Purpose never lived in the instructions; it lived in the discipline of the code around them, and where that discipline is absent, or has been deleted, the instruction carries on doing its small exact thing to no end whatsoever.
