Instructions: Flow

Everything so far has been about producing values. This page is about what the CPU does next: how it decides, how it calls a routine and finds its way back, and how it loops. Ten instructions cover all of it, and one blunt fact underneath them explains the rest: a return is just four bytes popped off the stack into the program counter, and nothing anywhere remembers what those bytes were for. Get that one fact and the tail call, the jump table, and the classic crash all stop being tricks. Every example is real, pulled from the Sonic 2 disassembly and re-verified line by line, unless it is labelled "Teaching example", which a handful are: those are written to make one point clearly and carry that label where they sit.

1 · Returning, the dumb version

Start here, because every idiom later on this page is this one fact used deliberately or broken by accident.

rts takes the four bytes sitting on top of the stack, copies them into the program counter, and moves the stack pointer up by four. That is the entire instruction. It does not know it is "returning". Nothing marked those four bytes as a return address when they were written, nothing inspects them when they are read, and the stack itself has no idea what it is holding. If those four bytes happen to be an address a caller left there, execution resumes in the caller and everything looks like a tidy function return. If they happen to be a saved register you forgot to pop, the CPU loads that number into the program counter and starts executing whatever is at that address.

Hold on to the phrasing, because the wrong model is the natural one: a newcomer expects rts to remember who called, the way a high-level language seems to. It remembers nothing. The pairing of a call with a return is a convention that code keeps with itself, and the processor enforces none of it. Motorola built one instruction that pops an address into the program counter; everything else is discipline.

New here? · What a subroutine call actually is

A subroutine is just a block of instructions somewhere else in the ROM that you would rather not copy and paste at every place you need it. "Deleting an object" is fifteen instructions, and forty different objects need to do it, so it is written once and the forty places jump to it.

The problem that creates is getting back. Forty callers jump to the same fifteen instructions, so the last of those instructions cannot say "jump to caller number 17"; it has no way to know which one arrived. The answer the 68000 uses is that the caller leaves a note. bsr writes the address of its own next instruction onto the stack and then jumps. When the routine finishes, rts reads that note back and jumps to it. The note is what makes one shared routine usable by forty callers.

The part worth internalising is how little the machine invests in this. The note is four ordinary bytes in ordinary RAM. It is not tagged, not protected, and not distinguishable from a saved register or a piece of level data that happens to be sitting in the same place. The whole call-and-return system is those four bytes plus everybody agreeing not to disturb them.

A quick reminder · the stack, the program counter, and labels

Four things this page leans on constantly, each taught in full elsewhere. Pocket versions:

Hex. Every number on this page written with a leading $ is hexadecimal, base 16, where each digit stands for exactly four bits: $FFFF is 65535 and $4E75 is one 16-bit instruction word. Numbers & Notation, section 3 has a converter you can type into.

The stack is a region of work RAM with one register, a7 (also spelled sp), pointing at its top. It grows DOWNWARD: a push subtracts from sp then writes, a pop reads then adds. Nothing about the region is special; it is plain RAM, and the four bytes a call leaves there are plain bytes. The Programming Model page, section 5 owns this, and hosts a stack stepper that runs bsr.w, rts and rte over a live stack column byte by byte. If you want to watch the four bytes move, watch them there. This page does not rebuild it. The REGISTER is where the CPU keeps a few special cases, three of which apply to a7 and to no other address register: a byte push or pop moves it by 2 rather than 1, so it always stays even; an odd a7 raises an address error the moment anything uses it; and there are really two of them, a supervisor a7 and a user a7, with the S bit deciding which one the name reaches. The System page covers that pair.

The program counter holds the address of the instruction being fetched, and steps along by itself. Redirecting it is the only thing any instruction on this page does, which is the cleanest definition of what this page covers. A handful of others move it as a side effect of raising an exception, TRAP and CHK among them, and those belong to the System page.

A label is a name the assembler swaps for an address at build time. When you write bsr.w ReadJoypads, the assembled bytes contain a distance, not a name; the name is gone before the ROM exists. Addressing Modes, section 1 covers this and the # sign.

RTS pops a longword from the stack into the program counter, so execution continues at whatever address those four bytes spell. Reach for it as the last instruction of any routine a bsr or jsr called. It appears 1,740 times in Sonic 2, which makes it the sixth most common instruction in the file.

The flags row above is doing more work than it looks. Because RTS touches no condition code, a routine can set the flags on its last real instruction and let its caller branch on them after the return. That is a genuine calling convention in engine code: the routine's answer travels back in Z or C rather than in a register.

Three things in there are worth naming now, because they recur all over this page. First, the routine has TWO entry points. DeleteObject copies a0 into a1 and then falls straight into DeleteObject2, which does the actual clearing. A caller that already has the right pointer in a1 calls the second label and skips the copy. Both paths end at the same rts, and that single rts serves both, because it does not know or care which door you came in through.

Second, the loop in the middle is dbf, the counted-loop instruction that section 6 covers. For now: it decrements d0 and jumps back to the - label until the count runs out.

Third, the if and endif lines are not instructions. They are the assembler deciding at BUILD time whether to include the move.w, based on whether the object size divides evenly by four. Nothing in the ROM tests anything there; by the time the game runs, that line either exists or it does not.

Gotcha A routine's pushes and pops must balance on EVERY exit path, not just the common one. If a routine pushes a register and takes an early rts before the matching pop, that rts pops the saved register into the program counter instead of the return address, and the CPU jumps to a data value. There is no error and no warning; the machine did exactly what you asked. The stack stepper on the Programming Model page has a mode that runs this exact failure so you can watch the wrong four bytes land in the PC.
Encoding (one opcode word, $4E75)

RTS has no fields at all. The whole instruction is the fixed 16-bit pattern 0100 1110 0111 0101, which is $4E75. Two bytes, and if you have ever scrolled a hex editor over 68000 code you have seen 4E75 end routine after routine.

Its neighbours in that same block are worth knowing, because they are one nibble apart and mean very different things: $4E73 is RTE, $4E75 is RTS, $4E77 is RTR. Encoding from the M68000 Programmer's Reference Manual, the RTS, RTE and RTR instruction-format diagrams.

Now the convention. Because rts jumps to whatever is on top of the stack, a call is simply "push the right thing first". bsr and jsr push the address of the instruction immediately after themselves and then jump, so the routine they land in ends with an rts that finds exactly that address waiting. Two instructions, agreeing about four bytes of RAM.

A call and a return are nothing more than that agreement about four bytes, and the rest of this page is what happens when somebody takes the agreement literally. Section 5 ends a routine with a plain bra instead of a call, so the routine it jumps to returns to YOUR caller rather than to you. The same section overwrites those four bytes with move.l #Elsewhere,(sp) to send a return somewhere it never came from, and throws them away with addq #4,sp so a return skips a whole level. None of those are exotic instructions. They are all the same four bytes, edited on purpose.

2 · Goto or call, near or anywhere

Four instructions send the program somewhere else without asking a question first: bra, bsr, jmp, jsr. They look like four separate things to memorise. They are not. They are two yes-or-no choices, made independently, and the four names are just the four combinations.

The first choice is do you intend to come back. If yes, the instruction pushes a return address before it jumps, and it is called a call: bsr and jsr. If no, it just jumps, and it is a goto: bra and jmp. The second choice is how the target is written down. bra and bsr store a DISTANCE from themselves, counted in bytes, which is compact but limited in range and fixed at build time. jmp and jsr take a full effective address, which can be an absolute number or a value computed at run time, with no range limit at all.

Now the misconception, because it is the one that actually bites. It is natural to assume that reach and push are the same axis: that jsr "does more" than bsr, so it must push something bigger or different. It does not. Both calls push the identical thing: the full 32-bit address of the instruction immediately after them. A bsr whose target is forty bytes away and a jsr to a computed address in a completely different bank leave the same shape of note on the stack, and the same plain rts consumes either one without being able to tell which arrived. The two choices really are independent, which is exactly why there are four instructions and not two.

What DOES differ between bsr and jsr is the VALUE pushed, and only because the two instructions are different lengths. Here the rule is worth walking a byte at a time, since "the address of the next instruction" sounds like arithmetic the CPU invents:

One rule, two answers. The CPU is not adding 2 in one case and 4 in the other because it knows which mnemonic you typed; it pushes "where the next instruction begins", and the next instruction begins two bytes later or four bytes later depending on how long this one is. Every call on the machine follows the same rule, including jsr (a1), which is two bytes and therefore also pushes plus two.

New here? · Why a branch stores a distance instead of an address

You write bra.w MainGameLoop, so it feels as though the assembled instruction must contain the address of MainGameLoop. It does not. It contains a small signed number: how many bytes forward or backward to move. The assembler works that number out by subtracting, and the label is gone from the ROM.

Two consequences follow, and both matter in real code. The good one: because the instruction only ever says "go 300 bytes back", the whole block of code still works if you load it somewhere else in memory. Everything stays relative to itself. The awkward one: a signed 16-bit distance only reaches about 32K bytes either way, so you genuinely cannot bra from one end of a 2MB ROM to the other. That is not a limitation the designers overlooked; it is the price of the compactness, and jmp is the escape hatch when you need to cross the whole map.

This is the same PC-relative idea the Addressing Modes page, section 5 covers for data. A branch is PC-relative addressing applied to code.

Reach for it as the ordinary goto: the bottom of a loop jumping back to the top, an early exit skipping past code that does not apply, or the last instruction of a routine handing off to another one (which is the tail call, section 5).

BRA is doing two completely different jobs here. The bra.s MainGameLoop on the fifth line is the loop: run one frame's worth of whatever mode we are in, then go back and do it again, forever. That branch is the reason a Genesis game never "finishes"; the console runs this loop until it is switched off.

The eleven bra.w lines below GameModesArray are a different trick. They are a table you can JUMP INTO. Every entry is exactly four bytes wide because bra.w is four bytes, so multiplying a game mode by four lands you on one of them. The jsr GameModesArray(pc,d0.w) above does exactly that, calling into the middle of the table, and whichever bra.w it lands on immediately forwards it to the real routine. The andi.w #$3C,d0 above it is doing the alignment work: it forces the mode to a multiple of four and clips it to $3C, so the computed landing spot is always the START of an entry rather than two bytes into one. Landing mid-instruction would execute a displacement word as though it were an opcode, which is one of the more entertaining ways to crash a Genesis.

And note what happens on the way home. The jsr pushed a return address pointing at the bra.s MainGameLoop. The bra.w it landed on pushed nothing. So when SegaScreen eventually runs its rts, control returns past the trampoline entirely and lands back on the loop. Those eleven branches are invisible from the callee's point of view, and staying invisible is exactly why the table is built from bra rather than bsr. That is section 5's idiom, arriving early.

BSR pushes the address of the next instruction and then branches, so the routine it lands in can rts back. Reach for it whenever you want a nearby routine's work done and then want to carry on: it is the ordinary function call of 68000 code, and at 1,841 uses it is the fourth most common instruction in Sonic 2, behind only move, moveq and beq.

This is the joypad reader, and it uses bsr for a trick you cannot understand without knowing what the instruction does to the stack:

Read the last three lines slowly, because there is no typo. ReadJoypads calls Joypad_Read, which polls the port a1 points at and stores two bytes through a0. Control comes back. Then addq.w #2,a1 steps a1 to the second controller port, and the code does not call Joypad_Read again. It simply RUNS OFF THE END into it, because Joypad_Read is the very next thing in the ROM.

So the routine's body executes twice for the price of one call plus a fall-through. The first pass is a real call, and its rts comes back to the addq. The second pass is not a call at all: nothing was pushed for it, so when the body reaches its rts, the four bytes on top of the stack are whatever ReadJoypads's own caller left there. That rts returns two levels up, and it is correct that it does, because there is genuinely nothing left to come back to. Here is the consumer, the rts that both passes end on:

	move.b	d1,(a0)+	; Store pressed controller input
	rts

One rts, reached two different ways, doing the right thing both times without knowing which way it was reached. This is the mechanism from section 1 being used on purpose, and it is the same insight the tail call in section 5 rests on.

Cheaper cousins If the call is the LAST thing your routine does, do not use bsr followed by rts. Use bra to the same target and delete the rts: the callee's own return then goes straight to your caller. That saves 2 bytes and 24 cycles (the bsr's 18 becomes a bra's 10, and your rts's 16 stops happening at all), and keeps the stack one level shallower. Section 5 is about exactly this.

JMP takes a CONTROL addressing mode: one that names a place, and does not move a register as a side effect. That rules out four things a newcomer reaches for. jmp d0 will not assemble, because a data register is a value and not a place; put the address in an address register and write jmp (a0), which is the form real code uses. jmp a0 will not assemble either, and the difference is worth holding on to: (a0) means the memory a0 points at, which is where the code lives, while a bare a0 would mean the register itself. jmp (a0)+ and jmp -(a0) are refused because a jump has no business quietly editing a pointer. JMP continues execution at an effective address, pushing nothing. Reach for it in two situations: when the target is too far away for a bra, and, far more interestingly, when the target is not known until the game is running. Encoding aside: BRA and BSR are Bcc with two of its condition codes

All three branch instructions share one 16-bit shape: 0110 cccc dddddddd, where cccc picks the condition and dddddddd is the byte displacement. BRA is that pattern with cccc = 0000 and BSR is the same pattern with cccc = 0001. So bra is $60xx, bsr is $61xx, and every conditional branch is $62xx through $6Fxx.

That is also the answer to a question section 3 raises. The condition table has sixteen entries, but only fourteen of them are available to Bcc. The two missing ones are "always true" and "never true", encodings 0000 and 0001, and they are missing because Motorola spent those two slots on BRA and BSR instead. An "always true" conditional branch would have been exactly bra, so nothing was lost, and a call was gained.

3 · Conditions: what a branch actually tests

Here is the reframe the whole section rests on. A conditional branch does not compare anything. It cannot: it has one operand, a label, and no access to whatever you think you are comparing. What it does is read a few bits in the status register that some EARLIER instruction already set, and jump or not jump based on them.

That sounds like a technicality and it is not, because it means the instruction that set the flags decides what your branch means. Write cmp.w d1,d0 and then bcs, and you have asked "is d0 below d1". Write lsl.b #1,d0 and then the identical bcs, and you have asked "did a 1 bit fall off the top". Same instruction, same bits, completely different question, because the carry flag got there a different way. A branch is a question about the flags, never about the values.

Which instructions set which flags is the Math & Logic page's business, and its flags demo lets you run one and watch X, N, Z, V and C move. This page picks up on the other side: given flags that are already set, which branch reads which of them.

One consequence is worth stating before anything else, because it is a hazard rather than a nicety: since the branch reads flags rather than values, any flag-setting instruction slipped in between the comparison and the branch silently changes what the branch means. The two lines still sit next to each other on the page and nothing warns you. That is why every instruction entry in this wiki tells you what it does to the flags, and why instructions that deliberately leave them alone, such as lea and movea, are the safe ones to use in that gap.

New here? · Why the comparison and the branch are two separate instructions

In most languages you write if (a < b) and the comparison and the decision are one thought. In 68000 assembly they are two instructions, and the join between them is invisible. cmp.w d1,d0 subtracts d1 from d0, THROWS THE ANSWER AWAY, and keeps only the five flag bits describing what the subtraction was like: was the result zero, was it negative, did it need to borrow. Then blo looks at one of those bits.

Two useful things fall out of the split. The first is that anything which sets flags can feed a branch, not just comparisons. A subq that decrements a timer already reports whether the result went negative, so the code can branch on it without comparing anything, and real engine code does this constantly to save an instruction.

The second is the hazard. Because the join is invisible, ANY flag-setting instruction slipped in between the compare and the branch silently changes what the branch means. There is no warning and nothing to see; the two lines still sit next to each other on the page. This is why entries all over this wiki tell you whether an instruction touches the flags, and why instructions like lea and movea, which deliberately leave the flags alone, are useful in the gap.

The pairing that causes real bugs

Look at the Kind column again. There are two complete sets of "is it bigger" branches, not one. bhs, blo, bhi and bls answer for UNSIGNED values, where a byte runs 0 to 255. bge, blt, bgt and ble answer for SIGNED values, where the same byte runs -128 to 127. They read different flags because unsigned and signed comparison genuinely produce their answers in different places: an unsigned compare puts it in the carry, a signed compare puts it in the relationship between N and V.

Now the wrong model, stated plainly so it can be knocked down: it is natural to assume these are stylistic alternatives, and that a comparison is a comparison. They are not, and it is not. The bits being compared are identical; the two families give genuinely different answers about them, and each is correct for its own reading. Picking the wrong family is a real bug that assembles cleanly, runs, and produces wrong behaviour only for certain values.

The clearest case is one byte pattern. Suppose d0 holds 1 and you compare it against -1:

Teaching example · not engine code 
	cmp.w	#-1,d0		; d0 holds 1. This leaves N=0, Z=0, V=0, C=1
	bhs.s	Bigger		; unsigned: NOT taken. As unsigned, -1 is $FFFF = 65535
	bge.s	Bigger		; signed:   TAKEN.     As signed, 1 is greater than -1

Both branches are reading the flags left by the same comparison of the same bits. One says d0 is smaller, one says d0 is bigger, and neither is wrong: $FFFF really is 65535 when read as unsigned and really is -1 when read as signed. The flags carry both answers at once, in different bits, and your choice of branch is the choice of which reading is in force. If you have not met two's complement, the Numbers & Notation page, section 7 teaches it; the one-line version is that $FFFF and -1 are the same sixteen bits and the difference is entirely in who is looking.

This is not a rare edge case. Across every possible pair of 16-bit values, bcs and blt disagree about half the time. They agree perfectly on small positive numbers, which is exactly why the bug survives testing: it works on every value you tried and fails the first time a coordinate goes negative or a size passes 32767.

Gotcha Pick the family from the DATA, not from which mnemonic reads better in English. Sonic's position and velocity are signed, so comparisons on them want bge, blt, bgt, ble. Addresses, sizes, counters and array indices are unsigned, so they want bhs, blo, bhi, bls. Mixing them assembles without a murmur. beq and bne are safe either way, since equality of bits does not depend on how you read them.

Same instruction, two spellings: bcc/bhs and bcs/blo

You will now go and grep the disassembly for bcc, and you will find about a quarter of them. This is the layer of confusion underneath the signed and unsigned split, and it is worth a section of its own because it will otherwise waste an afternoon.

The assembler accepts bhs as another name for bcc, and blo as another name for bcs. Not similar instructions: the same instruction. There is one encoding for each (0100 and 0101 in the table above), and the assembler turns either spelling into the same two bytes. Nothing in the ROM records which name you typed.

So why two names? Because the one instruction has two honest descriptions, and which one is true depends on what set the carry. After a comparison, "carry clear" means "the first value was higher or the same", so bhs says what the code MEANS. After a shift or a rotate, carry is just the bit that fell off the end and there is no comparison anywhere, so bcc says what the code means. The s2disasm authors used the spellings deliberately to record which of those two situations each site is, and once you know that, the choice of spelling is a useful comment rather than noise.

Two predictions before moving on. Work each one out before opening the answer; both are cases where the obvious reading is the wrong one, and neither answer tells you anything this section has not already said.

1An object is moving LEFT at 16 pixels a frame, so x_vel(a0) holds $FFF0. This code is meant to catch objects moving RIGHT faster than 16. Is the branch taken?

Teaching example · not engine code 
	move.w	x_vel(a0),d0	; d0 = $FFF0, which is -16
	cmp.w	#$0010,d0	; compare it against +16
	bhi.s	TooFast
Show the answer

Yes, it is taken, so an object drifting left gets treated as one racing right. The subtraction the cmp.w performs is $FFF0 minus $0010, which is $FFE0. That result is not zero, so Z is clear. Its top bit is set, so N is 1. It needed no borrow, because as unsigned numbers 65520 really is bigger than 16, so C is 0. And it did not overflow, because as signed numbers -16 minus 16 is -32, which fits in a word, so V is 0.

bhi asks for C clear AND Z clear. It gets both, so it branches. Nothing malfunctioned: bhi is in the unsigned family, and read as unsigned $FFF0 is 65520, which is genuinely higher than 16. It is a correct answer to a question the code did not mean to ask.

The signed branch reads different flags. bgt wants Z clear AND N matching V, and here N is 1 while V is 0, so they disagree and bgt does not branch. Two mnemonics, one letter apart, opposite behaviour, and both assemble without a murmur.

Notice when this bug would have been caught, which is the reason it survives: it is right for every rightward velocity you could test with, and it only misfires once the object turns around.

2d0 holds exactly $0010. Does this reach IsSixteen?

	move.w	d0,d1		; keep a copy for the code below
	beq.s	IsSixteen

No. The copy destroyed the answer. The cmp.w did set Z, correctly, and then the move.w set it again from the value it moved. MOVE writes N and Z from the data it copies and forces V and C to zero, exactly as add and cmp do. It is not flag-neutral just because it did no arithmetic.

The value copied is $0010, which is not zero, so Z comes out clear and the beq falls through. The code assembles, runs, and quietly asks "was the copied value zero" instead of "was d0 sixteen".

The fix is to put the copy above the comparison, so the instruction immediately before the branch is the one you meant to test. The contrast worth carrying is MOVEA, the address-register form, which sets no flags at all: on this CPU, whether an instruction disturbs an answer already sitting in the flags is a fact you have to know per instruction.

This is the same point the four worked examples above make from the other direction. A branch has no idea which instruction armed it. It reads the flags as they stand, and the last instruction to write them is the one it is really about.

4 · Dispatch: calling something computed

Section 2 gave jmp and jsr a reason to exist that was true but boring: they reach further than a branch. This is the real reason. A branch's target is frozen into the instruction when the ROM is built and can never be anything else. jmp and jsr take an effective address, and an effective address can be worked out while the game is running. That one difference is what lets an object hold a number saying which of its behaviours it is currently doing, and lets the engine turn that number into a jump.

The mechanism is called dispatch, and it is why an engine's object code is a table of routine addresses rather than a chain of comparisons. Without it, running the right one of six behaviours means six compares and six branches, and the cost depends on which one you wanted. With it, it is one table read and one jump, the same cost every time, and adding a seventh behaviour means adding a table row rather than editing a chain.

New here? · How a number turns into a jump

Every Sonic object has a byte in its 64 bytes of RAM called routine. It is just a small number: 0 while the object is setting itself up, 2 once it is running, 4 while it is exploding, and so on. Nothing about the number is special. The trick is entirely in how the code uses it.

Next to the object's code sits a jump table: a plain list, one entry per behaviour, in the same order as the numbers. Because every entry is the same width, the number times that width is exactly how far into the list the right entry sits. So the code reads routine, uses it to index the table, gets an address out, and jumps there. Six behaviours, one jump.

The one thing this buys that a chain of comparisons cannot is that the object CHOOSES its own next behaviour simply by writing a different number into that byte. It does not have to know where any of the code lives. You will see addq.b #2,routine(a0) all over engine code, and it always means "advance to my next state"; the increment is 2 rather than 1 because each table entry is a word wide.

Here is the idiom, complete, with both ends on one screen. This is the object that runs the "start" banner in the Special Stage:

Obj5F:
	moveq	#0,d0
	move.b	routine(a0),d0
	move.w	Obj5F_Index(pc,d0.w),d1
	jmp	Obj5F_Index(pc,d1.w)
; ===========================================================================
; off_70FE:
Obj5F_Index:	offsetTable
		offsetTableEntry.w Obj5F_Init	;  0
		offsetTableEntry.w Obj5F_Main	;  2
		offsetTableEntry.w loc_71B4	;  4
		offsetTableEntry.w loc_710A	;  6
		offsetTableEntry.w return_723E	;  8
		offsetTableEntry.w loc_7218	; $A
s2disasm/s2.asm:9617-9630 (Obj5F, the Special Stage start banner)

Four instructions. moveq #0,d0 clears the whole register, then move.b drops the one-byte state number into the bottom of it, so the top of d0 is known to be zero and the register can safely be used as an index. Then the two steps that matter.

move.w Obj5F_Index(pc,d0.w),d1 reads a word from d0 bytes past the table's start. jmp Obj5F_Index(pc,d1.w) then jumps to d1 bytes past the table's start. So the table does not hold addresses at all: it holds OFFSETS from its own beginning, which is what the offsetTableEntry macro builds (it assembles to dc.w of the target minus the table label). Read an offset, then jump that far from the table.

Two things are bought by the extra step. Each entry is a word rather than a longword, halving the table. And because nothing in the table or in either instruction is an absolute address, the whole object can be assembled anywhere in the ROM and still work; the (pc,...) form means every address is worked out relative to where the code currently is. That form is the program-counter-with-index mode, and the Addressing Modes page has the full derivation of how it computes its address, which this page does not repeat.

Note also that this is a jmp and not a jsr. Nothing is pushed. Obj5F does not want control back; whichever routine the table sends it to will run that state's behaviour and rts straight to whoever called Obj5F. That is the tail call, and section 5 is about doing it deliberately.

The second shape is a plain function pointer held in a register, with no table at all. This is the Nemesis art decompressor, which has to write each decoded row somewhere, and which of four ways it writes depends on how it was entered:

	; writes the row to its destination with the appropriately determined function
	jmp	(a3) ; dynamic jump! to NemDec_WriteAndStay, NemDec_WriteAndAdvance, NemDec_WriteAndStay_XOR, or NemDec_WriteAndAdvance_XOR

Deciding once and then jumping cheaply forever is what a function pointer buys you, and it is also why code like this is hard to follow without a debugger. Same two-step table read as Obj5F, with the same andi.w alignment guard section 2 described (masking to $3E keeps the index even, so it can only land on the start of a word-wide entry). But this one is a jsr, and the three lines after VintRet are exactly why.

Whatever routine the table picked, this handler still has bookkeeping to do afterwards: bump the frame counter, restore the fifteen registers it saved on entry, and return from the interrupt. If the dispatch were a jmp, none of that would happen, the registers would stay trashed, and the interrupted code would resume with a corrupted stack. So the rule is not "tables use jmp"; it is the ordinary one. Use the goto when the current routine has nothing left to do, and the call when it has.

Gotcha A computed jump is only as safe as the arithmetic feeding it. Every dispatch above masks its index first (andi.w #$3C, andi.w #$3E) so the value can only land on an entry boundary and cannot run off the end of the table. Nothing in the hardware checks this: if a state byte is ever set to a number the table has no row for, or an odd number when the entries are words, the jmp will happily go to the resulting address and execute whatever is there. An odd address is at least loud, because the 68000 raises an address error the moment it tries to fetch an instruction from one. A wrong but even address is silent, and is one of the classic ways a modified object crashes several frames after the actual mistake.

5 · The tail call, and other deliberate abuse

Section 1 said rts jumps to whatever four bytes are on top of the stack and has no memory of who called. That was the mechanism. This is what you can do with it, and the answer is: quite a lot, because "whatever four bytes are on top of the stack" is something your code is allowed to arrange.

Start with the commonest case. Suppose the last thing your routine does is call another one and then return:

Teaching example · not engine code 
	bsr.w	Inner		; push a return address, go and run Inner
	rts			; Inner came back to here; now go back to OUR caller

Look at what those two instructions accomplish between them. The bsr pushes an address whose only purpose is to reach an rts that immediately pops the previous address and leaves. Four bytes are written and read back for nothing. So delete both instructions and write one:

Teaching example · not engine code 
	bra.w	Inner		; go and run Inner, pushing nothing at all

Nothing was pushed, so when Inner reaches its own rts, the four bytes waiting on top of the stack are the ones YOUR caller left. Inner returns straight past you to whoever called you. It cannot tell the difference and does not need to: it pops four bytes and jumps, exactly as it always does.

This is the tail call, and it is free in every direction. Two instructions become one, so 2 bytes of ROM are saved (bsr.w plus rts is 6 bytes, bra.w alone is 4). It saves 24 cycles: the call drops from 18 to a branch's 10, and your own rts's 16 stops happening at all. The stack stays one level shallower for the whole of Inner's run. And there is no catch, provided you genuinely had nothing left to do afterwards.

If you have read the PEA entry on the Moving Data page, you have already met this idea from the other end. There, pea pushes an address that no call put there, so a later rts "returns" somewhere it was never called from: a fake call, built by writing the stack by hand. Here, a call declines to push, so an rts returns further back than it should. Both work for one reason, that rts does not check anything, and running into the pair from opposite directions is what usually makes the mechanism click.

Here is the best six lines in the disassembly for this. It is the object that draws the score numbers that pop out when you destroy a badnik:

Obj29_Main:
	tst.w	y_vel(a0)		; test speed
	bpl.w	DeleteObject		; if it's positive (>= 0), delete the object
	bsr.w	ObjectMove		; move the points
	addi.w	#$18,y_vel(a0)		; slow down
	bra.w	DisplaySprite
s2disasm/s2.asm:24790-24795 (Obj29_Main, the floating score numbers)

Read the last line, then read the whole routine again looking for an rts. There is not one. This routine can never return under its own power, and it is completely correct.

Every exit is a tail call. If the number has stopped rising, bpl.w DeleteObject leaves for good, and DeleteObject's rts (the one from section 1) returns to whoever called Obj29_Main. Otherwise the routine moves the sprite, slows it, and bra.w DisplaySprite leaves for good, and DisplaySprite's rts does the same job. The one ordinary bsr.w in the middle is the only call here that expects to come back, because there really is work after it.

Note the contrast that line makes, since it is sitting right there: bsr.w ObjectMove and bra.w DisplaySprite are the same distance, the same width, and differ only in whether the routine wanted control back. That is section 2's first axis, chosen twice in four lines for two different reasons.

Conditional tail calls, and why they read as jumps into nowhere

That bpl.w DeleteObject deserves its own beat, because it is the form most likely to stop a reader. A conditional branch whose target is a different ROUTINE is a tail call wearing a branch's clothes. There is no bsr, no jsr, and nothing that looks like a call at all; a line that appears to be a local "skip ahead if positive" is in fact this routine's entire exit path.

It reads as a jump into nowhere until you know the idiom, and it is not rare: counting only branches whose target is one of the five common shared routines, there are 21 of them in Sonic 2. The tell is the target name. bpl.s + is a local skip; bpl.w DeleteObject is an exit.

Nineteen lines with no rts either. Every one of its three exits is a bra.w to another routine. Three routines deep in source terms, one stack level in fact, and one rts unwinding all of it. If you set a breakpoint on that rts and looked at the stack expecting three return addresses, you would find one.

Return-address surgery

A reader working through the PEA entry asked the question that opens this part, and it is exactly the right one: is there something like PEA, but it overwrites?

There is no such instruction, and there does not need to be. A return address is four bytes of RAM at the address sp holds. Reaching them needs no special instruction because (sp) is an ordinary address-register-indirect operand and every instruction that can write memory can write there. So:

  • move.l #Elsewhere,(sp) replaces the return address, and the next rts goes to Elsewhere instead of home.
  • addq.l #4,sp throws the return address away without reading it, so the next rts pops the address BELOW it and returns one level higher than it was called from.

The second of those is the one real engine code actually uses, and it uses it 20 times in Sonic 2. It is worth framing as an idiom rather than a curiosity: it is how a routine says "whatever my caller was going to do after calling me, do not do it."

; sub_13D10:
Obj34_Wait:
	subq.b	#1,anim_frame_duration(a0)	; subtract 1
	bne.s	+				; if it's not 0, branch
	move.b	#1,anim_frame_duration(a0)	; reset to 1
	rts
; ---------------------------------------------------------------------------
+	addq.w	#4,sp	; don't run the code after the call to this routine
	rts
s2disasm/s2.asm:27161-27169 (Obj34_Wait, part of the title card)

The comment states the contract in plain English, which is unusual and welcome. This routine has two ways of finishing. If the timer has not run out, the plain rts on the sixth line returns normally and the caller carries on. If it HAS run out, the addq.w #4,sp discards the caller's return address and then rts pops the one underneath, so control leaves the caller entirely.

Here is one of its five callers, so you can see what gets skipped:

; loc_13D58:

On the ordinary path, Obj34_Wait returns and the two lines after the jsr run. On the timer-expired path, they do not: the whole of Obj34_BottomPartIn after the call is skipped, and control returns to whoever called IT. Five callers get that behaviour without any of them containing a test for it, which is the point. The check lives in one place, and the way it reports "and stop" is by editing the stack.

The price is that the trick is invisible from the call site. Read Obj34_BottomPartIn on its own and nothing about jsr Obj34_Wait(pc) suggests the two lines after it might never run. That is a real hazard when you are modifying code you did not write. Two of the three sites in this section say so in a comment; the Big Ring one below does not, and is correspondingly harder to read. If you write this idiom, comment it.

New here? · Why would a routine ever want to cancel its caller?

It looks rude, and the first reaction is usually that the caller should just check the answer itself. So why not do the obvious thing: have Obj34_Wait return a yes-or-no, and have each caller test it?

Because there are five callers. The obvious version means five copies of the same test and branch, five chances to get one of them wrong, and five places to edit when the rule changes. The surgery version puts the decision in the routine that owns it, once, and the callers stay as short as they were. What the routine is really saying is not "here is an answer" but "we are done for this frame", and that is a statement about the whole call chain rather than about one return value.

The reason it is available at all is the theme of this page. In a language with real function calls you would need an exception or an early return that the compiler understands. Here the return address is four bytes of RAM, so "do not go back there" is just an instruction that moves a pointer. The machine offers no protection and also asks no permission.

The cost is that it is invisible from the call site. Reading Obj34_BottomPartIn on its own, nothing suggests the two lines after the jsr might not run. That is a real maintenance hazard, and the disassembly is inconsistent about warning you: this site and the Oil Ocean one state the contract in plain English, while the Big Ring one leaves a bare addq.l #4,sp to speak for itself. If you write this idiom, comment it.

Gotcha addq.w #4,sp and addq.l #4,sp are two different encodings that do exactly the same thing here, and both spellings really do appear in Sonic 2 (this site uses .w; the two below use .l). That is not sloppiness: when the destination is an address register, the manual states that "the entire destination address register is used regardless of the operation size", so a word-sized ADDQ still adds to all 32 bits of sp. Note this is a free choice between .w and .l only: addq.b into an address register is not legal at all, since the manual permits only word and long operations there. And do not carry the habit anywhere else, because for a data register destination .w and .l are genuinely different instructions.

6 · Loops

You can build a loop out of what you already have: a counter, a subq, and a bne back to the top. The 68000 also gives you one instruction that does all three, and Sonic 2 uses it 412 times. It is also the instruction on this page most often described wrongly, so it is worth being exact.

DBcc Test Condition, Decrement and Branch DBcc Dn,<label>

Flags Xunaff. Nunaff. Zunaff. Vunaff. Cunaff. changes no flags even though it decrements a register, which is the fact the dbeq example below depends on
10 cycles best case: the looping iteration, condition false and the count still running Three cases, not two, and it is worth knowing all three: 10 when it loops, 12 when the CONDITION ended the loop, 14 when the COUNTER ended it. So the exit is slightly dearer than the iterations, and the two kinds of exit cost different amounts. Always 4 bytes. From the M68000 User's Manual, Table 8-9.
Counter DnAn(An)(An)+-(An)d(An)d(An,Xn)(xx)#nd(PC)

Nine crosses and one chip: the counter must be a data register, and only its LOW WORD is used. A counter in memory, in an address register, or as an immediate will not assemble. The target is a label, always a signed 16-bit displacement, so a DBcc loop body can be up to about 32K bytes long but the instruction has no short form. The size is fixed at word and you cannot write dbf.l.

DBcc runs a counted loop. Reach for it whenever you know how many times to go round: it replaces a decrement and a branch with one 4-byte instruction, and it is the standard shape for copying a table, clearing a block of RAM, or walking a list. The version you will actually meet is dbf, which is 411 of those 412 uses.

New here? · What this loop looks like if you build it by hand

Nothing forces you to use DBcc. A counted loop out of parts you already have looks like this, and it is worth writing out once so you can see exactly what the one instruction is replacing:

Teaching example · not engine code 
	moveq	#24,d1	; 24 here really does mean 24 times
.loop:
	; ...the body...
	subq.w	#1,d1	; count one off
	bne.s	.loop		; not zero yet, go round again

Two instructions at the bottom instead of one, so 6 bytes instead of 4, and roughly 12 cycles a pass instead of 10. Those are small numbers until you notice this shape appears hundreds of times in a ROM, which is why Motorola gave the loop its own instruction.

But the difference that actually matters is the third one, and it is not about size at all. subq.w SETS THE FLAGS, which is how bne knows what to do. So a hand-built loop destroys any comparison the body made, and a body that wants to report something back has to stash it somewhere before reaching the bottom of the loop. DBcc changes no flags at all, so whatever the body last compared is still readable after the loop ends. The dbeq example further down this section is built entirely on that difference.

Notice too that the hand-built version counts to ZERO and the DBcc version counts to MINUS ONE. Every bit of the off-by-one below comes out of that one difference: the two loops are not the same loop with different syntax, they stop on different values.

Here is the order of operations, in the manual's own order, because getting it in the wrong order is the usual mistake:

  1. Test the condition first. If it is TRUE, stop. Fall through to the next instruction, and do not touch the counter at all.
  2. If it is false, subtract 1 from the low word of Dn.
  3. If the result is -1, stop and fall through.
  4. Otherwise branch back to the label.

Two things in that sequence surprise people. The first is that the condition is a reason to STOP, not a reason to continue. This is backwards from Bcc, where the condition is a reason to branch. The manual's own gloss is the clearest way to hold it: DBMI reads as "decrement and branch UNTIL minus". So dbeq means "loop until equal", not "loop while equal".

The second is what makes dbf the one you see. F is the condition that is never true, so step 1 never stops the loop and only the counter ever can. dbf is therefore a pure counted loop with no condition at all, which is what you usually want. The manual notes that most assemblers also accept DBRA as a spelling of DBF; the Sonic disassemblies do not use it, and there is no dbra in any assembly source in any of the three trees.

And the third is the counting. Because the branch happens when the result is not -1, the loop runs one more time than the number you loaded.

Gotcha Load N-1 to run N times. Work it through once and it stops being a rule to memorise: load d1 with 3, and the body runs, then the decrement gives 2 (not -1, so loop); body runs, decrement gives 1 (loop); body runs, decrement gives 0 (still not -1, so loop); body runs a fourth time, decrement gives -1, and only now does it fall through. Four passes from a 3. The zero pass is the one people lose, because a loop that ends on zero is what every other processor and every high-level language has trained you to expect. Loading 0 runs the body ONCE; if you want a loop that might run zero times, you have to test before entering it.

Real code makes the subtraction visible rather than leaving it to be remembered. This is the VDP register setup at boot:

The count is not a number at all, it is arithmetic the assembler does: the end label minus the start label gives the table's length in bytes, and the -1 is the off-by-one written down where you can see it. The comment then states the real answer, $18, which is 24. So 23 goes into d1 and the body runs 24 times. Writing it this way means that adding a row to VDPInitValues changes the loop count automatically, with no number anywhere to forget to update. This is a good habit to copy.

The smallest possible use is a loop with no body at all:

At 10 cycles a pass it costs roughly 18,000 cycles, which is a visible slice of a frame. It exists because the machine is PAL and the code wants to arrive at a particular moment.

Finally, the one instruction in Sonic 2 that justifies the whole DBcc family existing. There are 412 DBcc instructions in the file and 411 of them are dbf. This is the other one:

	lea	OilSlides_Chunks_End(pc),a2

	moveq	#OilSlides_Chunks_End-OilSlides_Chunks-1,d1
-	cmp.b	-(a2),d0
	dbeq	d1,-

	beq.s	loc_4712
s2disasm/s2.asm:5551-5557 (Oil Ocean, searching a chunk list)

This is a table search, and it can end two different ways: it found the byte, or it ran out of table. dbeq handles both in one instruction. The condition EQ stops the loop the moment cmp.b reports a match, and the counter stops it if the table is exhausted. Neither exit needs its own branch.

Which leaves the question the last line answers: after the loop, which of the two happened? The beq.s can still tell, because DBcc changes no flags. The Z flag sitting there is still the one cmp.b set on the final pass, untouched by the decrement and by the loop exit. So beq.s means "we left because we found it". A loop built by hand out of subq and bne could not do this: the subq would have overwritten Z, and the code would need to stash the comparison's answer somewhere first.

Note also the -(a2). The pointer was loaded with the END of the table and each cmp.b steps it backwards one byte before reading, so the search runs from the last entry to the first. Predecrement and DBcc compose naturally for a reverse walk, because both count downward, and reversing the direction costs nothing here since a search does not care which end it starts from.

Encoding (one word, $5xC8 through $5FCF, plus a displacement word)

0101 cccc 11001 rrr followed by a 16-bit displacement, where cccc is the same four-bit condition as section 3's table and rrr picks the counter register. So dbf d1,Loop is $51C9 plus a displacement word: condition 0001 (false), register 001.

Unlike Bcc, DBcc gets all SIXTEEN conditions, including the 0000 and 0001 that Bcc lacks, because the encoding space here is not being shared with anything. dbf is condition 0001 and dbt is 0000, and dbt is close to useless: the condition is always true, so it stops immediately every time and the loop never runs. 3d1 is loaded with $00010000, which is 65,536. How many times does the body run, and what is left in d1?

The body runs once, and d1 ends up holding $0001FFFF. DBcc only ever looks at the LOW WORD of the counter, and the low word of $00010000 is $0000. So the body runs, the dbf subtracts one from that low word, the low word becomes $FFFF which is -1, and the loop falls through. The high word is never read and never changed, which is why the 1 is still sitting up there afterwards.

The tempting answer is 65,537, the loaded count plus the extra pass, and it would be right if you could write dbf.l. You cannot: the size is fixed at word and the assembler refuses the long form. The register you name is really a 16-bit counter that happens to be living in a 32-bit register, so a loop that needs more passes than a word can count has to be built as a loop inside a loop.

Note also that the answer is one pass and not zero. That is the same off-by-one as always: the exit test is "did the decrement produce -1", never "did it produce zero", so a low word of $0000 gets exactly the one pass that loading 0 gets.

The compare runs once, and d1 still holds 5. DBcc tests its condition before it touches anything else. EQ is true, so the loop stops right there, and the subtraction never happens at all. The tempting answer is six passes, and it comes from reading dbeq as "loop while equal". It is the other way round, and the section above gives you the phrasing that keeps it straight: dbeq means "loop UNTIL equal". The condition is a reason to STOP, which is backwards from Bcc, where the condition is a reason to go, and reading the two the same way round is the usual mistake.

The timings tell the same story if you would rather not take it on trust. DBcc costs 10 cycles when it loops, 12 when the CONDITION ended the loop, and 14 when the COUNTER did. The condition exit is the cheaper of the two exits precisely because it skips the decrement.

There are three return instructions and they are not interchangeable. All three pop a program counter off the stack; they differ in what else they pop, and getting that wrong does not produce a wrong answer, it produces a jump to a number that was never an address.

Use rte where an rts belonged and the CPU pops six bytes for a frame that is only four: the top word becomes the status register, and the program counter is assembled from the remaining two bytes plus whatever happened to be underneath. Use rts where an rte belonged and it pops four bytes from a six-byte frame, so the saved status word becomes the top half of the program counter. This is the same class of failure as the unbalanced stack in section 1, wearing a different costume: the bytes were fine, the count was wrong.

RTR pops a WORD into the condition codes, then a longword into the program counter: six bytes in that order, so the word sits on top. Only the low byte of that word matters, the five condition codes; the manual is explicit that the supervisor half of the status register is left alone. Reach for it when a routine must return with the flags exactly as some earlier moment left them, and you have arranged for a matching word to be on the stack. That is rare, and RTR appears zero times in Sonic 2.

It does appear in modern engine code, in the one situation that genuinely calls for it: resuming something that was interrupted partway through. The saved address is pushed first as a longword, then the saved status word on top of it, which is exactly the order rtr will read them back. Two moves and an rtr restore the program counter and the flags in a single indivisible step, which is why this is better than jumping and then trying to restore the flags afterwards: any instruction you used to jump would clobber the flags you were trying to restore.

RTE ends an exception handler. On the 68000 an ordinary exception, such as an interrupt, pushes six bytes: the status register as a word and then the program counter as a longword. RTE pops both back. (Two exceptions push more. A bus error or an address error, the kind section 4's gotcha describes, pushes a fourteen-byte frame that puts the faulting access address and other diagnostic words ON TOP of the usual pair, which is why a handler that reads the usual pair naively prints nonsense for exactly the two failures you most want to debug: the first word it finds is not the status register at all. The Programming Model page's exception section states the same difference and carries the vector list.) That is the same shape as RTR and it is a different thing: RTR restores the five condition codes, RTE restores the ENTIRE status register, including the interrupt priority mask and the supervisor bit. Restoring the mask is the point, because that is how the machine stops being inside an interrupt.

You have already seen the only kind of RTE a Genesis game contains, at the end of the vertical interrupt handler in section 4: movem.l (sp)+,d0-a6 to put the registers back, then rte. There are four rte instructions in the whole of Sonic 2, which is a normal number for a game. They are not one per handler, though: V_Int and H_Int_Done have one each, and PalToCRAM has two, because it has two exit paths. That is worth noticing, since each of those paths has to leave the stack in the same state, which is the gotcha below.

This page deliberately stops here. Which exceptions exist, what the vector table is, what the CPU pushes when things go wrong, and how a handler reads the frame are all covered on the Programming Model page, section 6, and RTE's full treatment belongs with the rest of the system-control instructions on the System page. What this page owes you is the comparison at the top of this section: it is a return, it pops more than RTS, and swapping the two is a crash.

Gotcha An exception handler's stack must be exactly as the CPU left it when the rte runs, and handlers are the easiest place to get that wrong because they are entered without being called. Every register the handler saves must be restored, along any path out. The movem pair at the top and bottom of Sonic 2's V-int handler is doing that job, and if any branch inside skipped the second movem, the rte would read six bytes of saved register data as a status register and a program counter. The stack stepper on the Programming Model page has an exception-and-rte mode that walks the six bytes one at a time.

Scc writes a single byte: $FF if the condition is true, $00 if it is false. That is the instruction as designed. In practice, Sonic 2 uses it 96 times and 88 of those are st or sf, whose conditions are the constants "always" and "never". Look at the beq.s. It comes AFTER the sne, and it is still testing the flags that tst.w set two lines earlier, because Scc changes no flags at all. So those four lines do two things with one test: they leave a $FF or $00 in d6 for later use, AND they branch on the same answer immediately. If Scc set flags the way most instructions do, this would need the test repeated, or the answer stashed and reloaded.

It is worth reading the pair in the right order, because the mnemonics are opposites and that looks like a contradiction at first glance. sne stores $FF when Z is CLEAR, which here means two-player mode is on. beq.s then branches when Z is SET, which means it is off. Same flag, two instructions asking for opposite answers, both correct.

Gotcha Scc is byte only. There is no seq.w and no seq.l, and the assembler will refuse them. That matters when the destination is a field the surrounding code treats as wider: s2.asm:27224 writes seq titlecard_location(a0) into an offset that the lines around it read and write with move.w and cmpi.w. The 68000 is big-endian, so the byte at that offset is the HIGH byte of the word, and the result of the seq is a word holding $FF00 or $0000 rather than $00FF or $0000. If you are reading code and the arithmetic afterwards looks like it is off by a factor of 256, this is usually why.

Scc also cannot be aimed at the video chip, which is easy to miss because it looks like a pure write. It is not: on the 68000 Scc reads its destination before writing the byte back, and the VDP's data port is a port with a direction rather than memory. Reading it while it is set up for writing makes the VDP withhold DTACK and stall the 68000. Sega's development manual lists Scc among the instructions it rules out for exactly this reason, alongside CLR, the shifts and rotates, and the bit instructions. The hazard is the video chip's rather than the 68000's, and The VDP & Planes carries the whole list and the mechanism behind it.

Cheaper cousins If you want 1 and 0 rather than $FF and $00, the manual's own suggestion is to follow the Scc with a neg.b on the same destination: $FF is -1, so negating it gives 1, and negating 0 gives 0. And if the condition is a constant, prefer st or sf over move.b #$FF, or clr.b for a byte destination: two bytes instead of four, which is exactly the trade those 88 sites are making.
Encoding (one word, $5xC0 plus the effective address)

0101 cccc 11 followed by the 6-bit effective-address field, so st d0 is $50C0 and sf d0 is $51C0. Compare that with DBcc's 0101 cccc 11001 rrr: Scc and DBcc share the same top ten bits, and DBcc lives inside the corner of Scc's address field that would otherwise mean "address register direct", which Scc cannot use anyway. That is the same trick that put BRA and BSR inside Bcc's condition field, and it is why both instructions get all sixteen conditions while Bcc gets fourteen. That is the whole of flow control on the 68000: two ways to reach a target, two ways to decide whether to, one counted loop, one way to keep an answer instead of acting on it, and three returns that differ only in how many bytes they take off the stack. The system, trap and stack-frame instructions, TRAP, CHK, LINK, STOP and the rest, are a separate page.

If there is one thing to carry away, it is the sentence from section 1: nothing marks those four bytes as a return address. Every idiom on this page, from the trampoline table to the tail call to the six-byte frame built by hand for an rtr, is code taking that fact seriously.
