The Genesis

Tiles & VRAM

A plane names tiles; this page opens the thing being named. An 8x8 tile is 32 bytes, one hex digit is one pixel, and 65,536 bytes of video memory divided by 32 is 2048, which is exactly as far as the 11-bit tile index reaches. Everything else here is what those 2048 slots cost: the tables that take their bite first, the auto-increment used as a layout tool, the two hazards that make an odd address or a byte-sized access a trap, and the 128KB video memory configuration a stock console does not have.

This page builds on The VDP & Planes, which teaches that the CPU reaches video memory only through two ports and a command word and that a plane is a grid of 16-bit words whose 11-bit field names a tile. Everything that machinery is pointing AT is here.

1 · One memory, and everything in it

VRAM is 65,536 bytes, addressed byte by byte, and it is the only general-purpose store the VDP has. The 68000 cannot address a single byte of it: everything goes in and out through the two ports, one command word at a time, which is the previous page's whole section 2.

Everything you met on that page lives in here. The tile art. The nametable for plane A, the one for plane B, and the Window's. The list of sprites. The horizontal scroll table. The colour memory and the vertical scroll memory pointedly do NOT: they are separate, fixed-size stores inside the chip, and they are the colour page's subject. VRAM is the one that has to be budgeted, because it is the one everything shares.

Here is the number the rest of the page turns on. A tile is 32 bytes, and 65,536 divided by 32 is 2048. That is also exactly how far an 11-bit tile index reaches: 0 to 2047. The field and the memory were sized to each other, so nothing that fits is unnameable and nothing nameable fails to fit. Say it precisely, because the loose version of this sentence is everywhere: video memory can address 2048 aligned 32-byte pattern slots, and the tables above take their share of those 2048 before a single tile of art is loaded. It is not a ceiling on what the console can draw. A slot holds one tile and the maps name a tile as often as they like, so a hundred cells can all point at the same slot, and the backdrop colour sitting behind the whole picture is not a tile at all.

New here? · Why is video memory so small?

Sixty-four kilobytes sounds like an odd amount to build a games machine around, so it is worth seeing what it buys and what it does not.

Start with the picture. A full Genesis screen is 320 pixels across and 224 down, which is 71,680 pixels. This machine spends 4 bits on each one, so storing that picture as plain pixels costs 35,840 bytes. Video memory is 65,536 bytes. One still frame would eat more than half of everything, and there would be nowhere to build the next one.

So the machine does not store the picture. It stores a small library of 8x8 squares and a map saying which square goes where, and it draws the picture fresh out of that library sixty times a second. The map for a whole screen is 1120 entries of 2 bytes, which is 2240 bytes, and the squares are shared: a brick wall of 300 cells can be four squares used seventy-five times each. That is the trade the whole console is built on, and it is why the interesting unit of Genesis memory is not the byte but the tile.

What matters for reading the rest of this page is not why the number is 64KB, but that the number is FIXED, and that every table the chip needs is carved out of the same block as the art.

2 · The tile: 32 bytes

A tile is 8 pixels by 8 pixels, 4 bits per pixel, and therefore 32 bytes. Sega calls it a pattern, the assembly world calls it a tile, and it is the atom of everything the VDP draws: planes are made of them, sprites are made of them, the text on a title card is made of them.

The 32 bytes are laid out as four bytes per row, eight rows, in reading order. Row 0 sits at offset $00, row 1 at $04, and so on to row 7 at $1C. Four bytes is eight nibbles is eight pixels, so a row of the picture is exactly one longword of memory.

Now the detail that makes 4bpp data readable by eye, and the one worth learning as a sentence: the left pixel of a pair is the HIGH nibble. Sega's table spells it out bit by bit, with a byte's D7 to D4 carrying the four colour bits of the first pixel and D3 to D0 carrying the second. So one hex digit is one pixel, reading left to right, and a hex dump of tile art is not an encoding to be decoded: it is the picture, printed one character per pixel. That single fact is why anyone can debug Genesis art in a memory viewer at all.

New here? · What does "4 bits per pixel" actually mean?

A byte is 8 bits, and 8 bits split neatly into two halves of 4. Each half is called a nibble, and a nibble holds a number from 0 to 15, which is exactly one hex digit. That is not a coincidence: hex exists because it lines up with binary four bits at a time, and the numbers page tells that story properly.

So "4 bits per pixel" means each pixel is one hex digit, and each byte holds two of them. Sixteen possible values per pixel is where "16 colours" comes from, and packing two pixels per byte is where "32 bytes" comes from: 64 pixels, half a byte each.

Other machines chose differently and it changes everything downstream. One bit per pixel gives two colours and a tiny memory footprint. Eight bits per pixel gives 256 colours and costs four times what this machine spends. Four is the middle bargain, and the Genesis leans on it hard: a whole screen of art fits where a quarter of a screen would fit at 8 bits.

Teaching example · not engine code

A ring, invented for this page. Read each hex digit as one pixel: 0 is transparent, 7 is a light outline colour, B is gold. The digits ARE the drawing, which is the entire point.

	dc.l	$00777700	; row 0, at offset $00
	dc.l	$07BBBB70	; row 1, at offset $04
	dc.l	$7BBBBBB7	; row 2, at offset $08
	dc.l	$7BB77BB7	; row 3, at offset $0C
	dc.l	$7BB77BB7	; row 4, at offset $10
	dc.l	$7BBBBBB7	; row 5, at offset $14
	dc.l	$07BBBB70	; row 6, at offset $18
	dc.l	$00777700	; row 7, at offset $1C

Nothing in a tile is a colour. Each pixel's four bits are an INDEX from 0 to 15, and which set of sixteen colours it indexes is not the tile's business at all: the referencing word decides that, with the two palette bits the nametable word carries. The same 32 bytes drawn under a different palette are a different picture for no extra memory. What those sixteen colours are, how many a screen can show at once, and why the choice is only two bits wide are the colour page's material.

One index is special, and it is a format fact rather than a palette fact: index 0 is transparent, always, whatever the palette holds in that slot. A tile is therefore fifteen colours and a hole, not sixteen colours, and a tile of all zero bytes is not a black square; it is invisible. Index 0 means "draw nothing here", and it means that with no exceptions anywhere in tile or sprite pixel data. What the viewer sees in its place is whatever layer, or the backdrop, lies behind.

The backdrop is a separate mechanism and it is worth keeping separate. One VDP register independently selects any entry of colour memory to show wherever no plane pixel and no sprite pixel is drawn: it is chosen by a register, it is not a property of any tile, and it is not locked to slot 0. So index 0 on the bottom layer can genuinely look like a colour, which is the natural wrong guess and the reason to say the mechanism out loud: nothing was drawn there, and what shows through the hole is the backdrop the register picked. Which entry that register may name, and what the transparent index costs the colour budget, are the colour page's.

New here? · Why is one of the sixteen a hole rather than a colour?

Because something has to be behind everything else, and the chip has no other way to ask the question.

Picture Sonic standing in front of a wall. Sonic is drawn from tiles, and those tiles are square, but Sonic is not. The corners of every one of his tiles have to show the wall instead of him. The VDP is drawing pixel by pixel and needs a per-pixel answer to "is there anything here?", and the cheapest possible answer is to spend one of the sixteen index values on "nothing". No extra bit per pixel, no mask, no second pass.

The cost is real and it is the tile's, not the palette's: every tile on the machine has fifteen usable colours out of a palette of sixteen. Artists spend that fifteenth slot knowingly, and no tile buys its way out of it: a background tile that will always be behind everything still cannot use index 0 as a colour, because a hole is all index 0 ever is.

What confuses people is that the hole is not blank. On the bottom layer there is a colour in it, and it looks for all the world as though the tile chose that colour. It did not. The chip is showing the backdrop, which one register picked out of colour memory entirely on its own account, and it would show the same colour in the same place if that tile had never been drawn.

Play with the format rather than taking it on trust. Paint the grid below and watch the 32 bytes underneath change; the byte holding the pixel you touched lights up, and so does the single hex digit inside it, so "left pixel, high nibble" is something you can see happen rather than a rule to remember.

There is one variant of the format, and it belongs to a display mode rather than to the tile. In the double-resolution interlace mode a pattern is 8 pixels by 16 and occupies 64 bytes, and the tile index's lowest bit is ignored, so indices effectively step by two. The mode itself, and what it does to the frame, is the frame and interrupt material; the format change is noted here so the 32-byte figure is not read as universal.

A closing honesty note, because it explains an absence you would otherwise wonder about. Tile data almost never appears as source code in a shipped disassembly. Art ships as compressed or raw binary and is pulled in by an include directive, so the bytes in this section come from Sega's own diagram and from the invented example above rather than from a game. Arithmetic ABOUT the format is everywhere in real code, and the next section is built on a piece of it.

3 · A tile number, not an address

The eleven bits in a nametable word are a tile NUMBER, not an address. The conversion is one multiplication, and it works only because every tile is the same size:

byte address = tile index x 32

Eleven bits reach 0 through 2047, and 2048 tiles of 32 bytes is 65,536 bytes exactly. There is no index that points past the end of video memory, and there is no 32-byte slot in video memory that no index can name. That is the tidiest fit on the machine, and it is why the index field is eleven bits wide rather than ten or twelve.

Sonic 2 gives the conversion its own name, and the whole body of it is a mask down to eleven bits and a shift left by five, which is multiplication by 32:

tiles_to_bytes function addr,((addr&$7FF)<<5)
tiles_to_words function addr,tiles_to_bytes(addr)/2
tiles_to_longwords function addr,tiles_to_bytes(addr)/4
s2disasm/s2.macros.asm:265-267

The mask is the same $7FF the nametable word uses, which is a small piece of evidence in itself: the helper and the hardware field agree about how wide a tile number is. And the helper has a consumer with a name a player would recognise. The art for the giant Sonic on the SEGA logo screen is aimed at video memory by tile NUMBER, and the macro turns that number into the address the transfer needs:

	dma68kToVDP SegaScreenScaledSpriteDataStart,tiles_to_bytes(ArtTile_ArtUnc_Giant_Sonic),\
	            SegaScreenScaledSpriteDataEnd-SegaScreenScaledSpriteDataStart,VRAM
s2disasm/s2.asm:78114-78115 (the SEGA logo screen's giant Sonic)
Gotcha Writing a byte address where a tile number belongs puts your art 32 times too far away. The two numbers are both plain integers and neither carries a label, so nothing complains. A tile at $0400 in the art pool is tile number $20, and a nametable word holding $0400 names tile 1024, which is somewhere else entirely. If a screenful of graphics comes out as garbage that looks like OTHER graphics, this is the first thing to check.

Where may tiles live? Anywhere. Sega's own inventory of video memory says the areas may be overlapped, and Charles MacDonald puts the same fact the other way round: patterns can be placed anywhere, even in the parts of other tables that are not being used, such as a spare corner of a nametable or a sprite table. The pattern generator's base is documented as fixed at $0000, and that is a statement about COUNTING rather than about placement: tile numbers are counted from the start of video memory, so index 0 is the 32 bytes at $0000 and index 700 is the 32 bytes at $5780. Any 32-byte slot in the whole 64KB has a number, including the slots that happen to sit under a table.

New here? · What is the difference between a number and an address?

An address is a place. A number is a count. The confusing part is that both are written as hex and the machine cannot tell them apart, so the difference lives entirely in what the reading code does with the value.

Think of a shelf of identical boxes, each 32 centimetres wide. You can identify a box by saying "the box 96 centimetres along" or by saying "box 3". The two are the same box, and converting between them is multiplying or dividing by 32. Neither is more correct; they are two ways of naming the same thing, and which one a given piece of the machine wants is something you have to know.

The VDP wants both, in different places. The nametable word wants box numbers, because they are shorter: 11 bits instead of 16, which leaves 5 bits over for the flip, palette and priority flags. The transfer machinery wants centimetres, because a copy has to land at an actual place. That is the whole job of a helper such as tiles_to_bytes, and it is why a Genesis codebase tends to have one.

The eleven bits are also worth respecting as a budget. A game that keeps all its art below tile $400 never uses the top bit of the index, and one shipped game noticed and spent it: the SEGA screen's streak wipe borrows bit 10 of each stored nametable word as a run-length flag, which is only legal because those particular tiles live low enough that the bit is free. It is a rare thing to catch a shipped game doing, and it is what makes a bit budget feel like money rather than like bookkeeping.

4 · What else lives in VRAM

Art is the bulk of video memory but it is not alone in there. Five tables share the same 65,536 bytes, each with a base register of its own and each with its own idea of how finely that base can be positioned.

Before the sizes, a distinction the next section's budget stands on. Three different quantities all get called a table's size, and they are not the same number. Blurring them is how a VRAM budget ends up either too gloomy or too cheerful by a couple of hundred tiles:

The quantityWhat it isWhy it is the one that bites
The aligned address windowThe region the table's base granularity and fixed shape reserve, whether or not the table fills it.The base register can only sit on those boundaries, so this is what the table costs as PLACEMENT, filled or not.
The span the VDP fetchesWhat the chip actually reads out of that window while drawing a frame.This is what the display costs, and it can be a small fraction of the window.
The useful bytesThe bytes carrying data the game meant to put there.The remainder is reclaimable for art, but only if the game deliberately shares it.

They come apart in both directions. A plane's whole map is useful and only the cells on screen are fetched this frame, because scrolling brings the rest on. The Window's map is the other way round: it reserves a large aligned region and fetches a few rows out of it. Two things in that table are easy to read past. The Window's map has a fixed SHAPE rather than a fixed cost. Its rows are 64 cells wide in a 40-cell display however narrow the Window itself is, and its base is aligned to $1000, so it sits inside a 4KB-shaped region whether it covers three rows or twenty-eight. What the chip actually fetches is only the rows the Window covers, and the remainder is space a game may fill with art, exactly like the unread part of the scroll table's aligned kilobyte. MD-OS, the program section 5 takes apart, says as much in its own equate: VDT_Window = $E000 ; $400 (max, depending on art, can do 3-4 lines before art is overwritten) MD-OS/Equates.asm:28.

And per-row and per-line scrolling cost the same space as each other, because a row-mode entry sits at the offset it would occupy in line mode, so the table still spans the same 896 bytes with seven eighths of its entries unread; what per-line scrolling spends over per-row is transfer time each frame rather than memory. The full-screen mode is the cheap one, and only because the chip reads just the first entry pair out of the whole table.

The sprite table's eight-byte entries, and what each field in one means, are the sprite material's business. Here it is simply a resident with a size and an alignment, and the alignment is the part that costs: in a 40-cell display it has to start on a 1024-byte boundary even though it uses 640 bytes, so 384 bytes of that window carry nothing at all unless the game deliberately puts art in them.

The teaching point of this section is what the table does not say. None of the five tables' positions is chosen by the hardware. What the hardware fixes is how finely each one may be placed, which is the granularity column; where inside that grid the table actually sits is the program's call. The program writes a base register and the VDP believes it, so a Genesis game's video memory layout is a layout somebody chose, and two games choose differently. The one thing that is not movable is where tile numbering starts, and as section 3 said, that is a counting convention rather than a wall. Sega goes further and says the areas may deliberately overlap, so one table can be shared between the scroll planes and the Window rather than duplicated.

New here? · Why does the program get to say where the tables go?

Because the chip has no idea what a game is going to look like, and hardwiring the answer would make the memory worse rather than simpler.

Every one of these tables has a size that depends on choices the game makes. A plane can be 2KB or 8KB. The Window can be absent. The scroll table can be read twice a frame or 448 times. If the VDP fixed the addresses, it would have to fix them for the biggest case, and a game that used none of the optional features would be paying for all of them in dead space it could not reclaim.

So the chip asks instead. Each table gets one small register holding the top bits of its address, and the game answers once at startup, or several times per frame if it wants to get clever. The cost of the arrangement is that there is no universal Genesis memory map to learn: each game has its own, and the only way to know one is to read the register writes. The next section is what one such map costs.

5 · The budget

The unit an art pipeline thinks in is not bytes, it is tiles, so this is where to think in tiles too. There are 2048 slots. Every table above takes its share of them first, at 32 bytes to the tile, and what is left is the art budget. Here are two setups worked out end to end, a modest one and a heavy one, both worked for a 40-cell display, using nothing but the sizes from section 4 divided by 32. Read the two totals as a range and the dependency as the thing that moves you along it. The top pair is what the tables cost if every aligned window is treated as spent, which is the figure to plan with unless somebody has actually written the sharing code. The bottom pair is what they cost once the unfetched remainders are filled with art, which is a decision, not a property of the hardware: in the modest setup the scroll table's kilobyte is fetched four bytes deep and the other 1020 are only free if a game puts something there. The overlap allowances quoted in sections 3 and 4, Sega's and MacDonald's, are what make the sharing legal at all; MD-OS at the end of this section is a program taking the offer up.

Three notes on the individual rows. The heavy setup's window row is 12 tiles fetched rather than 8 because in a 40-cell display the Window's map rows are 64 cells wide whatever the Window's visible width is, so three rows of it cost 3 x 64 x 2 bytes. The plane rows carry one number rather than two because a plane's map is fetched a screenful at a time and useful all the way across: none of it is a remainder anybody can reclaim. But the plane rows do hide an alignment of their own, and it is charged to neither total: both plane bases move in units of $2000, so in the modest setup each 4096-byte map sits in an 8192-byte slot, and the spare half cannot hold the other plane. It can hold art, or a table with a finer granularity, which is exactly what games put there, and that is why it is not counted as a cost here. The framing of a VRAM budget in tiles, and both of these worked setups, come from rasterscroll's VDP overview. The totals here are not that source's: they are re-derived from the sizes in section 4, and on the fetched counting the heavy setup comes out six tiles below the figure printed there. Every step of it is on the page to be checked.

Now the number that makes the budget bite. A 40-cell display is 40 cells across and 28 down, so filling the visible screen once with tiles that repeat nowhere costs 1120 of them. Against 2048 slots that is more than half of everything the index can name; against the 1476 the heavy setup has even with every remainder shared, it is more than three quarters. plutiedev puts the practitioner's version of the same warning as a rule of thumb: there is room for up to 2048 unique tiles, but assume more or less 75% of that once the tables have taken theirs.

That arithmetic is the whole reason Genesis art looks the way it does. Repetition, mirroring and re-colouring are not a style; they are the budget. Both of the cheap tricks are free in the same 16-bit word: the nametable word's two flip bits give a mirrored copy of any tile for no extra bytes, and its two palette bits give a recoloured copy the same way, which is the colour page's story.

New here? · Why does so much Genesis art repeat?

Because a designer who does not repeat runs out of memory before the level is one screen long, and the numbers are not close.

Take the heavy setup above, at its most generous: 1476 tiles for everything, and that already assumes the game reclaims every unfetched corner of the tables. One screenful of never-repeating scenery is 1120 of them, which leaves 356 for Sonic, every badnik, every ring, the HUD, the monitor boxes and the next screen you are about to scroll into. A level is dozens of screens long. The arithmetic simply does not work unless most of the picture is the same few hundred squares arranged differently.

So the craft goes into building tile sets that repeat WELL. A cliff face is a handful of squares with edges that line up in several combinations. A checkerboard hill is two tiles. A mirrored pair of tiles makes a symmetrical arch out of half the art, because the flip is a bit in the map rather than a second copy of the pixels. And a palette swap turns one tileset into an evening version of itself for nothing at all.

Once you know this, you can see it. Look at any Genesis background and start counting distinct 8x8 squares; you will run out of new ones very quickly, and that is not laziness, it is the machine.

A real map makes it concrete, with one caution attached: this is ONE game's map, not THE map. Sonic 2 states its layout as equates whose comments derive the sizes from first principles, and the sizes are hardware arithmetic while the addresses are Sonic 2's own decision:

The two _2P entries are worth a second look: the same game keeps a SECOND set of plane map addresses for its split-screen two-player mode, which is the previous section's teaching point in one game's own constants file. The positions are the program's call, and this program makes the call twice.

Now compare Sonic 3 & Knuckles, which runs on the same silicon and writes its own bases for the same tables:

The lesson is sharper than "two games, two maps". Two of those three tables moved and one did not. The Window went from $A000 (s2disasm/s2.asm:1437) to $8000, and the horizontal scroll table went from $FC00 to $F000, a full 3KB away ($FC00 - $F000 is $C00, which is 3072 bytes). But dc.w $857C is $7C times $200, which is $F800, and that is Sonic 2's sprite table address to the byte. Two teams working independently on the same silicon landed on the same address for one table and picked differently for the other two, which is what a layout being a CHOICE actually looks like: not arbitrary, not fixed, just decided. Sega's own worked example of a complete layout, which places every table for a 32-cell display and leaves the rest to art, is on the previous page and is worth comparing against both.

What happens if you refuse the tile abstraction entirely

The sharpest way to feel what naming tiles buys you is to watch a program decline it. MD-OS, a homebrew operating system for the Mega Drive, wants a paint program, and a paint program wants pixels rather than a tile library. So it writes plane A's nametable exactly once, at startup, with 1120 tile numbers that never repeat, in column order:

		move.w	#$8F80,(a6)					; set auto-increment amount
		move.l	#$80008000|((VDT_ArtPaint/$20)<<$10)|((VDT_ArtPaint/$20)+1),d0 ; prepare starting tile ID
		move.l	#$00020002,d1					; tile increment
		movev	VRAM, VDT_PlaneA, d3				; set VDP write address
		moveq	#(320/8)-1,d2					; width of plane

	.NextX:
		move.l	d3,(a6)						; set plane address
		addi.l	#$00020000,d3					; advance to next column
	rept	224/16
		move.l	d0,(a5)						; write tiles
		add.l	d1,d0						; increase tile IDs
	endr
		dbf	d2,.NextX					; repeat for all columns
MD-OS/Screen Desktop/Paint Layer/Setup Paint Layer.asm:8-21

Count what that loop writes. The column counter is (320/8)-1, which is 40 columns; the repeat block runs 224/16 times writing a longword, and a longword is two tile numbers, so it is 28 rows. Forty by twenty-eight is 1120, and the numbers step by two every longword and never come back. Every cell of the visible plane now points at a tile of its own, so writing to tile number N is writing to a fixed square of the screen, and plane A has become a linear 320 by 224 framebuffer at 4 bits a pixel.

The bill is exact, and the program states it as an equate:

VDT_ArtPaint_Size	=	((320*224)/2)		; $8C00
MD-OS/Equates.asm:23

$8C00 is 35,840 bytes, which is 54.7% of all video memory, permanently. It is also, to the byte, one screenful of never-repeating tiles from the paragraph above: 1120 tiles at 32 bytes each. The rest of the machine then has to fit in what is left, and the shape of the program shows it: plane A is the canvas, so the desktop wallpaper is on plane B, and the mouse cursor is a sprite rather than something painted into the canvas, which is what keeps it from damaging the picture underneath every time it moves. This is a homebrew program rather than a commercial one and it is quoted here as an existence proof of a technique, not as an authority on the hardware; what it proves is the cost.

6 · The auto-increment as a layout tool

Register 15 holds an auto-increment: a step the VDP adds to its internal address after every access, so a run of writes walks through video memory without the address being re-issued. That mechanism is the previous page's. What this section is about is that the step is a NUMBER you choose, and choosing it well is how a program decides what shape its writes have.

Four values do most of the work, and each of them is a different job:

StepWhat a run of accesses then walks
1consecutive bytes, which is what a VRAM fill wants
2consecutive words: ordinary tile art, ordinary nametable rows
4one tile ROW per access, so a run walks down the rows of a tile and then into the tile below
128one row of a 64-cell-wide nametable, so consecutive writes walk straight down a COLUMN of the plane

The last one is the trick worth carrying away. A scrolling game has to rewrite the column of cells that is about to enter the screen from the side, and a column is the worst possible shape for memory laid out in rows: on a 64-cell-wide plane the cells of one column are 128 bytes apart. Setting the auto-increment to that same 128 makes the column contiguous from the writer's point of view, so a column update becomes one address command and a straight run of words, the same cost as a row.

The shortest proof that the step is a live register rather than a constant is a macro that changes it and changes it back. A VRAM fill writes a byte at a time, so it needs step 1, and everything around it wants step 2:

	move.w	#$8F01,(a5) ; VRAM pointer increment: $0001
s2disasm/s2.macros.asm:34 (inside dmaFillVRAM) 
	move.w	#$8F02,(a5) ; VRAM pointer increment: $0002
s2disasm/s2.macros.asm:42 (the same macro, restoring it)
Gotcha The auto-increment is global state, and nothing resets it for you. A routine that sets it to 128 for a column update and returns without putting it back leaves every unrelated transfer for the rest of the frame striding 128 bytes at a time. The symptom is graphics smeared down the screen in stripes rather than a crash, which makes it a slow bug to find. The macro above is the pattern: set it, use it, put it back.

The framebuffer from section 5 leans on this register. Its paint routine sets the step to 4, one tile row, immediately before firing a transfer:

		move.w	#$8F04,(a6)					; set auto-increment to single tile row size
MD-OS/Screen Desktop/Paint Layer/Paint Layer.asm:480

Follow what that produces, because the shape is not the obvious one. A tile row is 4 bytes, so a step of 4 moves down one row of one tile and, at the bottom of a tile, straight into the top row of the tile below. But a WORD is only 4 pixels, which is half a tile row. So a linear run of words with this step paints a stripe 4 pixels wide and 224 lines tall, straight down through 28 stacked tiles. The program's buffer confirms the intent: it is 224 words, one per line of the screen. A narrow vertical stripe is not an obvious drawing primitive, and it is what falls out of the layout when tiles are stacked in columns. The transfer machinery wrapped around that write, and what it costs, is the DMA material.

New here? · Why would anyone want to write down a column?

Because the screen moves sideways, and the memory does not.

A plane's map is stored row by row, the way you would read a page: all of row 0, then all of row 1. That layout is perfect for anything that happens along a row and awkward for anything that happens down one, because two cells in the same column are a whole row apart in memory.

Now think about Sonic running right. The picture slides left, and every eight pixels of movement a new column of scenery has to appear at the right edge. Nothing else needs updating: the rest of the map is already correct and simply scrolls. So one of the most frequent bulk writes a side-scrolling game makes is exactly the awkward shape, one cell every 128 bytes, twenty-eight times over.

Without the auto-increment register you would pay for a fresh address command before every cell, which is two extra writes to the control port for each two bytes of payload. With it you pay for one address command and then let the chip do the striding. The register turns the awkward shape into the easy one, which is why it is a layout tool and not just a convenience.

7 · Byte access, and the byte-order quirk

Three separate hazards live in this territory and they blur together constantly, so here they are named and separated before any of them is explained. Two are this page's; one is not.

HazardWhat it isWhere it is taught

Byte access is void

Sega published the Genesis Software Manual and then published corrections to it. Two of those documents matter here: Technical Bulletin #14, "Corrections to the Genesis Software Manual", dated 1991-09-09, and the earlier corrections fax of 1991-04-17. Both carry the same correction, and its scope is exactly three memories: byte access to VRAM, CRAM and VSRAM is null and void. The manual's own text had implied byte writes to the data port were fine. Sega's own bulletin retracted it, which is a publisher correcting its own record, and the reason this track treats the manual's printed text as a claim to be checked rather than as a floor.

What a byte write actually DOES on the hardware is a separate question with a separate answer, and it is measurement rather than documentation: Charles MacDonald measured that a write to either VDP port is taken as a 16-bit write with the low byte duplicated into the high byte, whether the address written to was even or odd. The previous page teaches that, and the two statements fit together rather than fighting: the bulletin is the rule, and the measurement is what the silicon does to you when you break it. A move.b aimed at the data port is not ignored and does not fault. It writes a word you did not mean.

The A0 quirk

The other hazard is about the address you set INSIDE the VDP, not about the size of the access. Sega states it in one sentence: the VRAM address decode uses A15 through A1, and A0 specifies the data write FORMAT. Write data cannot cross a word boundary, and the high and low bytes are exchanged if A0 is 1. Separately, the manual notes that A0 does count towards the address increment even though it is ignored during decoding.

Read that as an aliasing rule and it makes sense. Video memory is organised in 16-bit words. The bottom address bit does not choose which half of a word you land in, because there is no mechanism for landing in half a word; it chooses whether the word you supply is stored as you wrote it or with its two bytes swapped.

Gotcha An odd video memory address does not address a byte. It swaps the bytes of the word. So a tile written at an address one byte off is not a tile shifted along by one byte, which you might spot; it is a tile with the two halves of every word exchanged, so each group of four pixels comes out as its second pair followed by its first. That looks like corruption rather than like an offset, and it sends people hunting for the wrong bug. Keep video memory addresses even.

Kabuto's hardware testing supplies the reason, and it is worth having because it turns an arbitrary rule into a consequence. The VDP's internal byte order is the opposite of the one the 68000 uses, and the chip's interface emulates the 68000's order so that ordinary word writes come out looking right. The A0 behaviour is what that emulation does when you ask for the odd case. The behaviour itself is stated by Sega and observable; the explanation is Kabuto's, from hardware measurement, and it is his alone.

New here? · Why would a chip care whether an address is odd?

Because "memory" is not one thing. It is a set of physical chips wired to a bus of a particular width, and the width leaks into what addresses mean.

The 68000 fetches 16 bits at a time and so does the VDP's memory. When something asks for "the byte at address 7", the hardware physically fetches the 16-bit word containing it and then picks a half. That picking is real circuitry, and a chip only has it if somebody designed it in.

The VDP mostly did not. Its address decode simply ignores the lowest bit, so addresses 6 and 7 select the same word, and the bit gets re-used for something else entirely: which way round the two bytes of that word are stored. Reading the number "7" as a place is therefore wrong; the 7 is a 6 plus a flag.

The 68000 has its own version of this same theme, and it is worth knowing they are not the same rule. Ask the 68000 itself to fetch a WORD from an odd address and it does not swap anything; it raises an address error exception and the program stops. Two chips, two different answers to odd addresses, both of them a consequence of a 16-bit bus.

8 · The 128KB mode, and register 1 bit 7

The VDP can be wired to 128KB of video memory instead of 64KB, and it is not done by adding a second bank. Two 64K chips are fitted, each holding ONE BYTE of every 16-bit word, and both are read in parallel, so address bit 16 becomes meaningful for transfer targets, plane maps, scroll tables and sprite tables. The mode is selected by bit 7 of register 1.

The epistemics here need stating plainly, and they split in two, because the bit's NAME and the bit's EFFECT are known in different ways. Take the name first. Sega's register page prints that bit as 0 and gives it no name at all. railgun's register reference documents it as the 128KB select, and Kabuto's hardware notes give the same identity while saying outright that it is what public documents say ("Bit 7 of VDP register 1 enables 128k mode according to public documents"). That is one chain rather than two legs: Kabuto is relaying the same documents railgun is, not corroborating them from the bench. Charles MacDonald's VDP document, written in 2000, calls the same bit "TMS9918 mode", a naming no later source reconciles with the 128KB reading. So the identity of the bit is documented, one source deep, and this page does not adjudicate the two names.

The EFFECT is the part somebody put on a bench. Kabuto measured what setting the bit does to a stock 64KB machine, and that measurement is what the rest of this section is built on. A regular Mega Drive is fitted with 64KB and nothing else; plutiedev names a machine that is not, the Teradrive, as an example rather than as a complete list. Set the bit on a stock console and Kabuto's measurement says exactly what happens: only the LOW byte of each word you write is stored, because the high byte is sent to a chip that is not there and is lost.

Which is the interesting part, and the reason this mode is worth a section rather than a footnote. Losing the high byte turns 128KB mode into a byte-granular write mode. Every word you push through the data port lands as one byte of video memory, which is precisely the thing section 7 says the hardware otherwise refuses to do. Kabuto measured the behaviour and named the technique "byte-wide DMA", and both halves of that belong to him rather than to any documentation. It comes with one condition that is not optional. With the bit set, the display garbles, so the whole technique lives inside the blanking interval, with the bit cleared again before the picture resumes. When the blanking interval is and how long it lasts is the frame and interrupt material.

Teaching example · not engine code

The shape of the technique, written out from Kabuto's account of it. Register 1's other bits here are an ordinary running configuration (display on, vertical interrupt on, transfers enabled, mode 5), and only bit 7 moves: $74 becomes $F4 and then goes back. As in the excerpts above, a6 is pointing at the VDP's control port.

	; inside the blanking interval only
	move.w	#$81F4,(a6)	; register 1 with bit 7 SET: 128KB mode

	; ... set the video memory address as usual, then push words.
	; On a stock console only the low byte of each word is stored, so
	; each word written paints exactly ONE byte of video memory.

	move.w	#$8174,(a6)	; bit 7 CLEAR again, before the display resumes

It is a labelled invention because no shipped game supplies one. In the five codebases surveyed while this track was researched, nothing sets the bit and nothing mentions the mode, so the honest statement is about those five and not about the medium: this is a capability of the silicon that the games we can read did not reach for.

Two other registers are reported to take part. Register 14 and register 6 are both printed as all zeros by Sega with no documented function, and single-sourced reports tie some of their bits to supplying that seventeenth address bit for plane tile data and for sprite art in 128KB mode. Kabuto corroborates that some register bits do this job but does not give the positions, so the positions are one source deep. They are in the reference box below, labelled, and no claim on this page rests on them.

New here? · What is a memory chip that only holds half of each word?

It sounds like a broken chip, and it is actually the ordinary way to build wide memory out of narrow parts.

Memory chips come in widths. If you have chips that are 8 bits wide and you want to read 16 bits at a time, you do not buy a 16-bit chip; you fit two 8-bit ones side by side, wire the same address to both, and read them together. One chip permanently holds the top half of every word and the other permanently holds the bottom half. Neither is "first" and neither is "second half of memory": they are two halves of every single word.

That is what the VDP's 128KB configuration is, and it is not a second bank you switch to. A second chip is fitted, each of the two is given the job of holding one byte of every word, and the pair is read together, so the total doubles and a seventeenth address bit starts to mean something. Leaving the second chip out and setting the bit anyway therefore does not halve your memory in the way you might guess. It costs you every high byte.
